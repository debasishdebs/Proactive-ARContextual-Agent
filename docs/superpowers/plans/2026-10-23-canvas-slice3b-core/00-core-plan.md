## 1. Goal

Let the user write a small Python function in the canvas and run it over photos/frames on the laptop in an offline container (`py.fn`, **ASYNC only**), after pairing a laptop helper with the phone, switching on the `py_exec` grant on the phone and confirming every run with a native tap on the phone. Everything the feature needs is in CORE: pairing, auth, native pairing and grant actions, the per-run native confirmation of every `py_exec` job, deletion fences for helper jobs, Room v8 (jobs and cleanup), job service and routes, S6 enforcement on every publish path, `py.fn` over photos/frames (WP8), dev-session lifecycle (S52), the single container runner with Podman sane defaults, browser UI, privacy suite, laptop helper core, doctor, Python live gate. **Stored sensor traces are not a canvas input in 3b (Option 1, section 24):** sensor experiments are run by the user on the laptop with the separate tool `tools/trace-lab` (WP14, no canvas, DB or phone integration). Release label stays `v1.0.0-alpha` (= Python experiments over frames, v0.9.3 COMPLETE). NL tool generation is **not** in this plan (section 3, backlog section "v2: NL tools").

## 2. Threat model A (binding, user ruling 2026-10-23)

The user's own laptop and own code. The user's function is **not** treated as deliberately hostile (it is the user's own Python on the user's own data); hostile-code hardening is the **3d hardening slice** (backlog): build with safety in mind now, sandbox and secure later. **The seams stay in CORE so 3d can tighten without redesign: one runner argv builder, one profile table, one resource config (`config/resources.json`).** Consequences:

| Kept (privacy and safety invariants) | Dropped to the 3d hardening slice (see backlog) |
|---|---|
| Pairing with fingerprint pin, native pairing and grant actions (a tap on the phone to accept a pairing and to turn the `py_exec` grant on, built directly on `HelperAuth`/`HelperGrants`, no HTTP surface), **per-run native confirmation of every `py_exec` job (a tap bound to one job hash, session and expiry; no HTTP surface; user decision 2026-10-23 evening)**, capability grants, helper token vs browser token separation | kernel quota loop-mount filesystem, process-tree forensics, report forgery tests, escaped-child sweep |
| Deletion fences: frame-Forget revision, Delete all, grant off, Disconnect all void helper jobs and the phone never acks after the event; laptop copies deleted by a persisted cleanup command | VM-side watchdog, heavy/light lock classes, launcher-crash reconciliation beyond section 8.1, exhaustive race/crash matrices |
| Room v8, additive (jobs and cleanup only; **v8 is 3b's, the Moment slice takes v9/v10 and 3c's migration moves after them, section 24**) | bounded regex language (`pattern` keyword is simply unsupported) |
| S6 refusal on every publish path; `PROTOCOL_VERSION` stays 1 (`helperProtocol = 1` is separate) | hostile collector catalogue, settings-isolation proofs |
| Single logger, count-only lines (always-on rule, section 12) | |

**Container sane defaults (one runner, one profile table; the same argv builder for every job):** rootless Podman, one named machine connection, **no host fallback** (no runtime = `needs_runtime` fail, never `subprocess` of job code on the Mac); `--read-only --cap-drop=ALL --security-opt no-new-privileges --user 10001`; memory = swap, cpus, pids limits; `--timeout` per profile; **network `none` for `py_exec` (the only CORE profile)**; **one job at a time** (`maxActiveJobs = 1`, `job.lock`; admission lock of section 8.1); **bind-mount sources are only under the job's `/stage/<jobId>/` subtree (the machine has exactly one mount, `$HOME/.pca-helper/stage:/stage`; inputs read-only), plus exactly one named volume `pca-job-<jobId>` at `/out`, created and journaled by the helper before the container starts**; scratch via `--tmpfs` size-capped dirs; **the job output goes to that job-local named volume mounted writable at `/out`, which survives container exit; the host does one bounded export and removes the volume (lifecycle in section 4.2)**; the collector refuses symlinks, non-regular files and oversize; free-disk check (`disk_low`); **`~/.claude` and `~/.codex` are never mounted.** Resource numbers are part A table 6 minus the loop-mount columns; WP12 may replace a cell with a measured value.

**No proxy in CORE.** The allow-list proxy (`container/proxy/*`) existed only for the CLI generation profile. Nothing in CORE needs network, so the proxy is dropped from CORE and from WP10; it moves to v2 with the `gen` profile (backlog).

## 3. Scope

**In (CORE):** helper protocol v1 and its shared fixtures (`py_exec` only; `jobType` field kept so v2 can add a type additively); pairing, the `py_exec` grant, native pairing and grant actions, **the per-run native confirmation of every `py_exec` job (HMAC-bound, no HTTP surface; user decision 2026-10-23 evening)**; Room v8 with the fenced job lifecycle and deletion fences (jobs, cleanup, `frame_forget_rev`; no result store); one `HelperJobService` modelled on `ReplayService` (one service, one port, one terminal fan-out); helper and browser routes; S6 on every publish path; `py.fn` ASYNC experiments over photos/frames through the existing `frameIds` run path with runner-level cancellation and the EXISTING `canvas_run_item` and fenced write paths (WP8); dev-session start/end with one termination operation, a session-owned network observer, four-hour user-canvas inactivity expiry and LAN-loss termination (WP6); browser UI; laptop helper (pair, poll, lease, heartbeat, kill, journal, cleanup, expiry, doctor/setup); one runner + profile table (one job row `py_exec`; `setup` and probe rows are non-job rows of the same table); Python in-container harness; VM-off preflight (host memory settings and two-build admission); spike A (machine with one `/stage` mount, admission lock, isolation probe); privacy suite; Python live gate; **`tools/trace-lab` (WP14): a laptop-side tool that decodes pulled trace chunk files and runs a user Python function over them locally; no canvas, DB, phone or helper integration (section 24)**.

**Out (v2 NL tools, backlog "v2: NL tools"):** the whole NL tool build path (CLI generation, `gen`/`verify` profiles, template and diff guard, Codex diff review gate, offline APK build, snapshot/verify driver, result bundle, `tool_build` grant and form, trusted example tool, spike B CLI + key and offline APK, S1/S3, API-key questions), `tool.draft` stand-ins and export, the 200-case schema oracle. **Out (3d hardening slice):** hostile-code defences LB1-LB9. **Out (carried over):** RT lockstep (LB11), LIVE, fusion tunables, Docker, second CLI, repair loop, watch app, mixed-domain projection, any sensing change. **Out (superseded by the Moment slice, backlog section J, user decision 2026-10-23 Option 1):** the stored-trace canvas input path: trace-item adapter and input contract (item selection route, `traceItems` estimate/start binding, `input.traceItems`), `TraceItemSource`, the trace provenance DTO, the retained result store with its fences, read API and run cascade, the stored-trace device gate, scores/notes on trace runs.

**Spike failure rule:** spike A (WP10) fail = no containers: ship only the phone half, no feature (status INCOMPLETE-GATED, scope review).

### 4.2 Output export and workspace lifecycle (Python path only; owned by WP12, used by WP13)

One job, one container, one export. There is no intermediate export, no reviewer step and no disk-backed build workspace in CORE (those belong to v2 NL tools, backlog). The container needs only `/stage/<job>/in` (read-only), size-capped `--tmpfs` scratch and the `/out` volume.

1. **Create.** Before the container starts, the helper writes `volume pca-job-<jobId>`, the stage dir and the planned export path into the cleanup journal, then creates the volume (`podman volume create`) and stages the inputs. The container mounts the volume writable at `/out`.
2. **Write.** The in-container harness writes `outputs.json` to `/out` and exits; the volume survives container exit. Cap enforced by the harness and again by the collector (py 32 MiB; WP12 may replace the cell with a measured value).
3. **Export (bounded).** After the container has exited, the host runs `podman volume export pca-job-<jobId>` into a pipe capped by `head -c <cap+1>` (cap hit = `too_large`) and writes `$HOME/.pca-helper/stage/<job>/export.tar`. Python extracts only regular files, refusing symlinks, hard links, devices, absolute or `..` paths, depth > 8, > 200 files and any file above its per-name limit (the WP12 collector). Free disk is checked before (`disk_low`).
4. **Collect and post.** The job glue (WP13) reads `outputs.json` from the extracted tree and posts the result to the phone.
5. **Retention (restored; applies at every terminal outcome: done, failed, cancelled, voided, expired).**
   - **Inputs and transient staging** (`/stage/<job>/in`, `export.tar`, the extraction tree) are deleted at every terminal outcome, whether or not a result was posted (`inputsDeletedOnJobEnd`).
   - **Outputs** (the extracted Python outputs and the volume) are deleted as soon as the phone has accepted the result (`committed` or `duplicate`), or at once on any failure.
   - **CORE retains no artifact.** For any retained artifact (none today; v2 APKs would be the first), the helper journal stores `expiresAt = createdAt + 7 days`, the artifact is removed at startup and by a periodic sweep, and earlier by a cleanup command; WP11 owns the metadata and the sweep and tests it with a synthetic artifact (`retention7d`).
   - Cancel, void, expire, every deletion-class denial and every phone cleanup command remove the volume, the stage dir and any artifacts dir (the journal drives it, so a crash is covered); the orphan sweep at helper start removes any `pca-job-*` volume that is not an open job.
6. **Tests.** `test_export_lifecycle` and the collector tests in WP12 (RED group), the live round trip in batch B2 (WP12 live); kernel quotas and hostile export fixtures stay in the 3d hardening slice (LB1, LB9).

- **Endpoints.** `POST /api/helper/pair` `{helperProtocol:1, code, name}` -> `{token, helperId, sessionGen, caps:{py_exec}, constants}`; `POST /poll` `{helperProtocol, active:[{jobId,leaseGen}], cleanupAcks:[id], ready:{py_exec}}` -> `{sessionGen, caps, serverTimeMs, available:[...], cancel:[...], cleanup:[{cleanupId, jobId|"*"}]}` (**CORE addition `ready`**: boolean from the helper's `python` stamp, held in memory, stale after 15 s, shown by `/api/helper-status`); `POST /lease` `{helperProtocol, types}` -> `{job:null}` or `{job:{jobId,type,leaseGen,leaseUntilMs,deadlineMs,bundleHash,payloadBytes}, serverTimeMs}` (absolute phone-clock ms, helper converts with `serverTimeMs`); `GET /jobs/{job}/payload?leaseGen=N`; `POST /jobs/{job}/heartbeat` -> `{leaseUntilMs, serverTimeMs}`; `POST /jobs/{job}/result` `{leaseGen,resultHash,result}` -> `{committed, duplicate}`; `POST /jobs/{job}/fail` `{leaseGen, code}`.

Payload max 1 MiB, result max 2 MiB; `py.sourceMaxChars 16000`, items <= 50 per job (= `CanvasRunner.MAX_PHOTOS`), 5 s per item, 120 s per job; `pyExecDeadlineMs 130000`; `confirmTtlMs 120000` (the tap window, from submit); `queueWaitMs 30000` (confirm to lease); `execWaitMs 135000` (lease to terminal = `pyExecDeadlineMs` + 5 s; **c8 #2: these three separate bounded waits replace part-B P10b's single 135 s submission-to-terminal timeout, so a late tap does not eat the execution budget**); the job deadline starts at lease, not at confirm; `maxActiveJobs 1`; cleanup retention 30 days on the phone; helper artifact retention 7 days.

After a deletion-class denial the helper deletes every laptop copy of the job at once and posts no result.

- **Shared contracts (WP1 only; owning modules in the WP1 row).** Schema subset `type, required, properties, additionalProperties:false, enum, items, minimum, maximum, minLength, maxLength, minItems, maxItems` (**no `pattern`**; a schema containing it is refused before the job is created).

- **Per-run confirmation (CORE, `py_exec` only; user decision 2026-10-23 evening; the design is the one retained in backlog V2, reinstated here).** Outer gate = the `py_exec` grant is on AND the user confirms this run. `HelperJobService` inserts every `py_exec` job in `AWAITING_CONFIRM`: payload not released, not leasable, not in `available`, so the helper learns nothing about it. The native card (`HelperConfirmActions`: `onConfirm(jobId)`, `onCancel(jobId)`, `pending()`) lists each pending job (input kind, item count, source size, countdown). `HelperConfirm` (`:phone`, memory only: an HMAC-SHA256 key generated when the dev session starts, never persisted, never in any HTTP body, header, log or backup) computes the tag over `jobId | bundleHash | sessionGen | confirmExpiresAtMs`; `HelperConfirmAdapter` (`:phone`) is the only caller of the port's `confirm(jobId, binding)`, which `HelperJobService` forwards to WP3's `confirmJobFenced` (one transaction re-checking state, expiry, bundle hash, session generation and `HelperFence`). ### 8.1 Admission lock (WP10; the small required part of LB6)

`pca_lock.py`, lock files under `~/.pca-helper/locks/`, **all non-blocking** (refusal = exit 75 `resources_busy`; nothing waits, so nothing deadlocks):

- **Host admission `host.lock`.** A host Gradle build takes it **shared**; the VM takes it **exclusive**. The two cannot overlap. **While holding the shared admission, the build also checks that the named Podman machine is stopped (`podman machine inspect`); a running, starting or unknown state returns `resources_busy`.** This covers a VM left running after an ordinary launcher crash (the kernel released the flock but the VM is still up).
- **Two build slots `slot-1.lock`, `slot-2.lock`.** A build also needs one slot lock (tries 1, then 2) held exclusively for the lifetime of its Gradle process. A **third build is refused**, whatever the shared admission says.
- **VM session.** `pca_lock.py vm-session` is a **long-lived owner process**. It takes `host.lock` exclusive **before the first step of the machine sequence (stopping the previous machine) and so before `podman machine start`** and holds it continuously across every VM step, every gap between steps and the 10-minute idle timeout, releasing it only after `podman machine stop` has been confirmed (machine state not running). **On a failed stop the owner does not exit: it stays alive holding the lock, reports `vm_stuck` on its control channel and on stderr, and retries the stop until recovery confirms the VM stopped (the controller or user can also stop the machine by hand; the owner re-checks the state).** A process cannot keep a `flock` after it exits, so exiting would silently drop the exclusion. Because the lock is held between steps, a host build is refused between two VM steps.
- **Helper jobs `job.lock`.** One exclusive lock serializes helper jobs (`maxActiveJobs 1`); it is independent of the build slots (a job needs the VM session; builds cannot run beside it).
- Not in CORE (stay in the 3d hardening slice, LB6): heavy/light classes, lifetime ownership of detached containers, launcher-SIGKILL and simultaneous-start barrier tests, full crash reconciliation (the VM-stopped check above, the orphan sweep and stale-lock release on process death cover an ordinary crash).
- Never `gradle --stop`; clean modules before trusting a red gate; no APK on GitHub; never uninstall the phone app (SQLCipher key); `adb install -r` only after a phone backup and never during a call; encrypted-migration open test only on `MyEmulator`.

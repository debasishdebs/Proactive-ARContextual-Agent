## 1. Forget scope
- (a) Developer-mode gate in the ENGINE. `ForgetScopeSetting.experimentalAllowed` (default false = fail closed, a throwing provider = false; `ContextApp` binds it to the Developer-mode flow). `ScopedForget.plan` throws `ForgetScopeNotAllowed` when the effective scope is Moment or Scene (explicit target or raised setting), and `ScopedForget.forget` re-checks the plan's effective scope, so a Scene confirmation opened before Developer mode went off does not run either. Photo scope and range Forget are not gated. Through `ForgetActions` the refusal is a `FAILED` outcome (nothing read or deleted). Existing tests that use Moment/Scene scope open the gate in their setup.
- (b) Batch peers: DECISION = keep the cascade, count it (not "leave peers alone"). Reason: the lineage token means one provider call produced the results of several photos (and later nodes derive from it), so a peer's stored result can carry text of the forgotten photo; leaving peers would reopen a residue hole in a deletion path, and the in-span path already deletes batch-wide. New `CanvasDao.batchPeersOf` (same token discovery as the delete); `MomentForget.discover` adds the peers of the outside cited photos to `Found.peerResults`, which is in the plan hash and in `Counts.peerResults`, plumbed to `ScopedPreview`/`ForgetPreview`, and the confirm dialog says "N other generated results from the same run will also be deleted (the next run recreates them)". A peer that appears after the preview changes the hash, so the delete is refused until previewed again. Test: `aBatchPeerOfAnOutsidePhotoIsCountedHashedAndTheOnlyExtraThingDeleted`.
- Not changed: single Photo/Fact scope (`singleCounts`) still cascades batch-wide uncounted, exactly as before (Photo scope is "as today"). If that should be counted too it is a separate, user-visible change.

## 2. Home chat to the glasses HUD
The chat already mirrored every typed answer to the HUD unconditionally (`VoiceGraph.mirrorTyped` through `PhoneDeps`), and a Query with target `glasses`/`both` recorded `no_glasses_path`. Now: `AnswerService.routeOf` gives the typed source (`AskActions.TYPED_SOURCE = "phone_typed"`) the real `DeliveryEnvironment.reach()`, so the same `DeliveryRoute.resolve` (connected + `glasses.display` capability) decides; `DeliveryRoute.mirrorsChatToHud` (explicit: `glasses`; `caller`: only without a fallback; no route = today) gates the one mirror call (`mirrorTypedAnswer`). Not connected / display off: phone, with `glasses_not_connected` / `glasses_display_off` recorded as for voice. Behaviour change to know: a chat Query published with target `phone` no longer mirrors to the HUD (before it did, ignoring the target). The queue/other sources still record `no_glasses_path`. Tests: `FlowPublishTest`, `DeliveryRouteTest`, `AppAnswererTest`.

## 3. Summarizer-pass pause
`NudgeEngine.runLocked` applies `triggers.paused()` (pause record or Battery Saver) to EVERY trigger, the summarizer pass and the built-in fallback included, before anything is read or called. Test `aPauseStopsEveryTriggerIncludingTheSummarizerPass` (no model call, no row; unpaused default Nudge still shows). One older test asserted that a failing plan lookup runs the built-in flow while paused; its pause was removed (the fallback test is about the lookup, not the pause).

## 4. Relaunch diagnostics (coordinator addition) and USER RULING 2026-10-28
- Diagnostics only: `RelaunchGuards.callInputs()` (default null; `AndroidRelaunchGuards` keeps the inputs of its last `callIdle`: `audioMode=<n> callState=<n|unreadable> sinceNormal=<bucket> sinceScene=<bucket>`, buckets `<15s <1m <5m <30m >=30m`, no numbers or names). `GlassesRelauncher` logs `relaunch: blocked (<why>) <inputs> poll=alive|idle for=<s> s` when the blocker or its inputs change (at most every 30 s) and as a heartbeat every 5 min while blocked, and `relaunch: block cleared (was <why>, <s> s)`. The existing `waiting (...)` lines are unchanged.
- USER RULING 2026-10-28: the relaunch guard blocks ONLY on a real call. `AndroidRelaunchGuards.callBusy`: audio mode `MODE_IN_CALL`, `MODE_RINGTONE` or `MODE_CALL_SCREENING`, or a readable telephony state that is not IDLE. `MODE_IN_COMMUNICATION` (VoIP, meeting apps) and every other non-NORMAL mode no longer block; `MODE_RINGTONE` (a ringing call) DOES block (follow-up ruling). The 15 s post-call settle now follows the end of a real call (mode or readable state); unreadable call state keeps the 30 s unknown-hold after a scene event. Media guard (full-screen reopen) unchanged. RISK: a VoIP call no longer defers the reopen (the app may be reopened over a VoIP call); the diagnostics line still logs the mode, so IN_COMMUNICATION being ignored is visible. Tests: `GlassesRelauncherTest` (`onlyARealCallModeIsBusy`, `aVoipModeLetsTheRelaunchProceedAndACallModeBlocksIt`, block logging), `AndroidRelaunchGuardsTest`. `GlassesWatchdogTest` needed no change (it stubs the relauncher's answer).

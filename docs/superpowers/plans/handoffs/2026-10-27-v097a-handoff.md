# v0.9.7 slice A handoff: configurable signals (branch feat/v097-signals, base v0.9.7 = v0.9.6)

## Design

### What exists today (all under android-companion/)
Sensors that feed signals
- Glasses IMU (gyro, linear accel, proximity for wear): `glasses/.../capture/motion/SensorFeed.kt` (`AndroidSensorFeed`, rates FULL/STILL/LOW at `SensorFeed.kt:89-90,179-181`, chosen by a rate policy; never user-editable). `glasses_imu` can NOT be switched off (`HudSettings.normalized()` strips it, `Protocol.kt` `motionSourcesOff`).
- Phone sources `phone_activity, phone_steps, phone_speed, phone_car, image_intent` and watch `watch_livefit`: on/off already user-editable (`phone/.../context/ContextSourceSettings.kt`, UI `ContextSourcesSettings.kt:194-197`). So "sensor on/off per source" EXISTS; sample/aggregation settings exist only as the fixed rate policy and `ContextSourcesSettings` switches.

Guard signals (catalogue)
- `core/capture/.../capture/plan/SignalCatalog.kt:30-36`: 7 per-second features (gyroMax, gyroMean, gyroRms, aboveOnFrac, accVar, stepHz, rotRad), `ctx`, `ctxAgeS`, alias `headSpeed`. Fixed list; `sigSchema 1/2`.
- Expression language: `services/ai/.../canvas/plan/ExprProgram.kt` (parse + type check + lowering, limits 32 nodes / cost 64 / 6 programs), `ExprLowering.kt`, glasses `PlanValidator.kt:77-97` re-checks 32 nodes / cost 64 / 8192 bytes.

Classifier constants
- Glasses motion classifier `core/capture/.../glasses/capture/motion/MotionClassifier.kt:275-283`: HEAD_MOVING_RAD_S 0.6, WALK_VARIANCE 0.5, WALK_MIN_HZ 1.5, WALK_MAX_HZ 2.5, RELAXED_VARIANCE 0.25, RELAXED_MIN_HZ 1.2, RELAXED_MAX_HZ 2.8, RELAXED_HOLD_MS 2000 (used at `:111`, `:247`, `:249`, `walking()`).
- Shadow heuristic `core/capture/.../motion/model/MotionModel.kt:27-29`: accVar 0.25, stepHz 1.2..2.8, aboveOnFrac 0.3.
- Glance tunables `GlanceParams.kt` are ALREADY plan-tunable (canvas head/threshold nodes, `PlanBounds`).
- Phone fusion (REST / WALKING / VEHICLE): `core/model/.../context/ContextFusion.kt:3-14` (`FusionParams`, e.g. stepsWalkPerMin 60, fastKmh 25); 11 keys are in the plan `phoneFusion` block (`PlanBounds.FUSION_DEFAULTS`) but no UI sets them and the hub is built with defaults (`ContextHub.kt:33`).
- S84 rule: the plan validator and compiler REFUSE sensing/classifier keys as plan parameters (`PlanValidator.SENSING`, `PlanCompiler.SENSING`). User ruling 6 of 2026-10-25 overrides this for classifier thresholds, but not through the plan: the plan stays untouched (default-capture hash `f5782e0d8610` cannot move).

### What becomes configurable
1. Classifier thresholds (glasses): the 8 MotionClassifier constants + 4 shadow-heuristic constants, as `ClassifierThresholds` (core:model) with per-key safe ranges, cross-checks (min < max) and clamping. Defaults EQUAL the constants.
2. Guard signal catalogue: a set of DISABLED catalogue signals (phone side, compile time). A guard that names a disabled signal fails to compile with `EXPR_UNKNOWN_SIGNAL` ("disabled in Settings"). Glasses catalogue is unchanged (still accepts everything), so old and new glasses behave identically.
3. Derived signals: user-defined named signal = an expression graph (same JSON as an `expr.guard` `graph`, VALUE-shaped: output number or boolean) over catalogue signals / window terms. A guard or value graph may name it (`"sig":"d_<name>"`); the compiler INLINES the definition as extra steps before the one validator pass, so limits (32 nodes, cost 64, 6 programs, 4 window terms, 8192 bytes) hold for the expanded plan and the glasses see only ordinary ops. `expr.guard`/`expr.value` stay `liveable=false`: derived signals are evaluated in SHADOW/TRIAL only. Operators stay extensible through the existing catalogue (no new language).
4. (not in this slice) per-sensor sample rates, phone fusion thresholds, user-defined sensors (v2).

### Storage
- Thresholds: additive optional field `HudSettings.classifier: Map<String, Double>` (only NON-default keys; empty = defaults), in the existing `pc_settings` store pattern (`CaptureSettingsViewModel.hud.update { ... .normalized() }`, like `markPhotoHoldMs`).
- Disabled signals + derived definitions: phone prefs file `signal_config` (store pattern of `WindowToleranceStore`: prefs + provider object read by every compile). Per-device, excluded from backup/transfer exactly like the canvas DB that holds the guards that use them (BackupRulesTest ruled; see Decisions).

### Transport to the glasses and the hash
- `HudSettings.classifier` rides `pc_settings` (Wire has `ignoreUnknownKeys`, so old glasses ignore it; PROTOCOL_VERSION stays 1). The glasses re-clean it (`normalized()`), apply it to `MotionClassifier` on the existing 1 s supervisor tick.
- `ClassifierThresholds.hash()` = `"default"` for no overrides, else 12 hex of SHA-256 over the canonical `key=value;` list. The glasses report the hash they run in an additive optional field `MotionHint.classifierHash` (sent on state changes and every 60 s), so the phone knows what runs (Settings shows "Glasses run this" / "waiting"). The trace records it through `TraceSettingsHash` ONLY when non-default (default hash text is byte-identical, golden traces unchanged; a change closes the trace with reason `settings`, which is right because behaviour changed).

### Validation, logging
- Every threshold passes `ClassifierThresholds.clean` (unknown key dropped, value clamped into range, min/max pairs kept ordered, equal-to-default dropped). Derived definitions pass `ExprProgram.parse/check` (same validator as guards/values) plus name pattern `[a-z][a-z0-9_]{0,15}`, max 8 definitions, no derived-in-derived, and an expansion probe so the length/limits are proven at save time.
- Logging by event name only (PcLog literals): `signal config saved`, `signal config rejected`, `classifier thresholds applied` (no values, no names).

### Defaults-unchanged proof
- Test pins `ClassifierThresholds.DEFAULT` to the literal old numbers and to `MotionClassifier` default behaviour; existing MotionClassifier / replay / golden tests (`CaptureSimulator`, parity, `ExprGraphGoldenTest`, default-capture hash test) must stay green unmodified.
- Empty `classifier` map and empty signal config produce byte-identical compile output (test compares planJson with and without the config object) and an identical `TraceSettingsHash`.

### Slice order (priority)
1. `ClassifierThresholds` + `HudSettings.classifier` + MotionClassifier/HeuristicMotionModel use + TraceSettingsHash + MotionHint echo.
2. Signal catalogue config (disabled set) + compile check.
3. Derived signals: model/store, expansion in `ExprLowering`, validation, shadow try-it works through the same compile.
4. Settings UI (thresholds page rows, signal list, derived editor) mirroring `window_tolerance`.
5. Remaining: phone fusion thresholds, sensor sample rates, canvas editor for derived signals.

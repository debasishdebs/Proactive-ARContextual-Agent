# Sensor features per Moment second (`moment_sensor`) handoff, 2026-10-24

Branch `feat/sensor` (worktree `~/Desktop/rokid/pca-sensor`), from v0.9.3 tip 00fdf9d9. Spec: `docs/superpowers/specs/2026-10-24-moment-scene-design-decisions.md` sections 2, 3, 5, 6 item 2, and the earlier `2026-10-23-moment-model-design.md` section 4 (canonical phone-second windows). TRACE_SCHEMA and PROTOCOL_VERSION are untouched.

## What is built
1. **Room v12, additive** (`11.json` untouched, `12.json` generated). `MIGRATION_11_12` is 2 statements (CREATE TABLE IF NOT EXISTS `moment_sensor` + index on `traceId`). `MigrationV11to12Test` is written like the v10 to v11 one (real exported schemas, JVM/Robolectric; all lineages 1..11 reach 12; additive-only scan). No SQLCipher/androidTest.
2. **Per-second features from a trace** (`core/capture`, `TraceSecondFeatures`): the frozen trace stores raw `g`/`a` samples and `cx` changes, NOT per-second feature rows (see "Finding" below), so the rows are computed with the glasses' own `MotionClassifier`, fed in append order with each sample's sensor time `sMs`; `tMs` only decides the phone second, through the trace's `ClockMap.phoneWall`. A sample the map cannot place (other boot, farther than the 60 s slack, wall or phone clock jump, no phone offset) belongs to no second and is dropped. The classifier runs continuously across seconds and only its accumulators are taken at each phone-second boundary (boundaries are at phone seconds, not elapsed multiples of 1000).
3. **`MomentSensors`** (orchestration): reads stored traces from `files/canvas_traces/<id>` on `Dispatchers.IO` and BEFORE the build transaction; eligible trace = live, not quarantined, `source = IMU`, `clockQuality = OFFSET_ESTIMATED`, `uncertaintyMs <= 500`, current deletion epoch, phone interval overlapping a requested second. Arbitration when several traces cover one second: most samples (`nGyro + nAcc`), then smaller trace id. A small cache (3 traces, keyed by id, revision and manifest hash) avoids re-reading on every 15-minute rebuild. Unreadable files give no row.
4. **`MomentBuilder`** (new optional `sensors` constructor argument, production wiring in `MomentTriggers` passes it): `build(ids)` and `rebuildWindow` read the traces first, then in the ONE build transaction re-check every trace used (`validTraces`: row present, not tombstoned, same revision, manifest, clock quality and uncertainty) and call `MomentDao.replaceSensor` for each built Moment. Deterministic and idempotent (identical rows write nothing and no audit row). A trace imported after the Moment was built backfills on the next build (the cadence rebuilds the previous and current hour; `build(ids)` of any second does it for that second). A Moment that no longer qualifies takes its row with it. With `sensors = null` the builder touches no sensor row.
5. **Deletion** (all in the caller's transaction):
   - `MomentDao.remove` (every Moment removal: Forget by id/range, source cleanup, builder removal) deletes the Moment's rows.
   - `CanvasSlice3Dao.tombstoneTrace` (reached by `forgetRangeTx`, which selects traces by interval overlap with the uncapped uncertainty over ALL live traces incl. UNMAPPED/QUARANTINED) deletes EVERY row computed from that trace in ALL Moments, also those outside the forgotten range.
   - `forgetRangeTx` also deletes rows by their own seconds inside `[from, to]` whichever trace they came from (covers a row whose trace row is missing).
   - `acceptTraceFenced`: a re-import of a trace id with other manifest content drops its old rows (the next build recomputes with the new revision); identical content keeps them.
   - Delete all: `WipeDao` (`momentSensor()`), `DeletionGraph` entry `moment_sensor` WIPED; `DeletionGraphInventoryTest`, `DeletionGraphWipeTest` (seeded) and `WipeDaoTest` pass.
   - Every change of the rows (`replaceSensor`, trace purge, between purge) hides the derived fields of the Moment AND of its Scenes in the same transaction through the existing `markStaleCore("MOMENT", ..., force = true)` (INVALIDATED + DERIVED_STALE/HIDDEN; `force` so the input revision moves even when no field was fresh, which refuses a derive that started earlier). The audit stays content-free: `refKind = SENSOR`, `refId = null`, step names from the closed list; no value, no trace id, test `theAuditNamesNoSensorValueAndNoTrace`.
6. **Readers**: `SensorSummary` (seconds, mean and max of gyro magnitude, acc variance, step frequency, most frequent motion state and context code). `Moment.sensor` (resolver built with the Moment DAO: `DaoMomentSource(dao, dao3, momentDao)`; the builder's own resolver is not and reads nothing), NOT part of `contentHash`/`contentRev`/`bindingKey` (test pins it). `GET /api/moments` JSON gets a `sensor` object only when a row exists. `SceneInputExecutor`: `SceneView.sensor` (over the member seconds) and `momentSensor` (per member), read in the same transaction as the Scenes; JSON keys appear only when rows exist. `PlanCompiler` untouched, no palette UI.
7. **Scene hook**: `DaoSceneSource` (not the pure `SceneCutter`) takes the Moment's activity from the photos' motion as before and, only when the photos logged none, from the `moment_sensor` second's `motionState`, counted only if in `SceneConfig.activityStates` (STILL, WALKING, VEHICLE; HEAD_MOVING and unknown names are not an activity). Golden test `noSensorRowsMeansExactlyTheScenesOfBefore`.

## Columns chosen (table `moment_sensor`, PK `(momentId, phoneSecond)`)
`momentId`, `phoneSecond` (epoch second, phone clock), `traceId`, `traceRevision` (which trace and row revision the numbers came from), `clockQuality`, `uncertaintyMs` (carried over from the trace's phone-clock row), seven REAL features in the order of the glasses' `SecondFeatures`: `gyroMax`, `gyroMean`, `gyroRms`, `aboveOnFrac`, `accVar`, `stepHz`, `rotRad`; `motionState` (classifier state at the end of the second: STILL, HEAD_MOVING or WALKING), `contextCode` (last `cx` ContextState name at or before the second, null before the first), `nGyro`, `nAcc` (sample counts: they show a partial first or last second and drive arbitration). Numbers, enum names and ids only; no raw samples. `momentId` is redundant with `phoneSecond` (it is its 8-digit hex) but both are kept because the brief keys by both and `momentId` is what every Moment delete uses.

**Finding.** The trace holds no per-second feature rows and no "activity" series: only `g`/`a` samples, `cx` (context state from the phone) and `sc.motion` (the motion state at each frame score, sparse). The per-second numbers therefore come from re-running the classifier (as the 2026-10-23 design section 4 intended), not from stored rows. Features are canonical-window features (windows aligned to phone seconds), not byte-equal to the glasses' drifting live ticks; the tests use hand-computed expectations, not two runs of the same code. `sc.motion` is not used (too sparse, and the classifier state per second is the same classifier).

## Decisions I made on my own
1. **Tolerance = 500 ms** of the trace's `ClockMap.uncertaintyMs` (`MomentSensors.MAX_UNCERTAINTY_MS`, from the 2026-10-23 spec 7.4 "larger than 500 ms may put a part one second off"). No such constant existed in code. The uncertainty includes drift and phone-sample age (up to 120 s), so many real traces will give NO rows. This is the "never guess" side; the number is one constant and a constructor argument. NEEDS A HUMAN LOOK on real traces (how many seconds survive).
2. PARTIAL traces are used (they are stored, viewable and replayable; the row carries no status). Easy to exclude in `eligible` if wanted.
3. One row per (Moment, second), not per (trace, revision) as in the earlier design: arbitration is done at write time (most samples, then smaller id) and the source trace id is stored. Losers are not kept.
4. Rows only for seconds that have a stored Moment (sparse rule): the sensor-only ephemeral seconds of the earlier design are not built. `momentId` and `phoneSecond` are both stored.
5. Features are computed per read of a trace (cached for 3 traces) rather than stored per trace at import time: import stays cheap and the frozen import path is untouched.
6. Audit: no new op or step names; the sensor change is INVALIDATED (+ DERIVED_STALE/HIDDEN) with `refKind = SENSOR` and no ref id, and nothing is written for a brand-new Moment (its BUILT row is its first revision).
7. Scene hook placed in `DaoSceneSource`, not `SceneCutter` (the cutter is pure and takes `SceneMoment.activity` as given); photos' activity wins when present (it was there first and the golden requires unchanged results); the sensor fills the gap.
8. The per-Moment "mean/max" summary is trivially one value (a Moment is one second); the Scene summary is where mean and max differ.
9. `GET /api/moments` gets the optional `sensor` object (it is the only place the Moment list reaches the canvas); `CanvasRunner` estimate tokens are unaffected: the resolver it gets also has the Moment DAO now, but `bindingKey` excludes the sensor summary (test pins it).

## NOT done

- The 500 ms tolerance and the classifier thresholds are untuned; no measurement on real pulled traces.
- `sc.motion`, `ep`, `gt` events are not copied.

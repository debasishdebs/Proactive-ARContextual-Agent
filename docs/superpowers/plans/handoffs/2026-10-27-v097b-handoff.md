# v0.9.7 slice B handoff: derived-signal editor, phone fusion thresholds, sensor recording (branch feat/v097-signals-b, base 2d2374c1)

## Design

### Item 1: Settings editor for derived signals (phone Compose, Settings > Capture > Signals)
- The expression IS the existing graph JSON (the language has no text syntax; the canvas JS stays untouched, `jsUnderSizeBudget` 4668 has no spare). The editor holds: a name field and a multi-line expression box with the graph JSON.
- Live validation = `DerivedSignals.validate(name, graph, current config)`, the very function `SignalConfigStore.saveDerived` (so `PUT /api/signals/derived/<name>`) calls. A JSON that does not parse is its own first problem. The first problem is shown; Save is disabled while any problem exists or the name/expression is empty.
- Save calls `SignalConfigStore.saveDerived` (no second write path), so the bounded 16-entry history, `remember`, wipe and logging by event name are inherited unchanged; replay of frozen versions is unchanged. Editing an existing signal loads its definition; delete stays as today. Shadow/trial only: nothing about liveability changes.
- Try-it: `ExprTry.run` needs per-signal series and a role; it cannot cheaply be driven from a one-line form without a second input editor. SKIPPED (Decision 1).

### Item 2: Phone fusion thresholds
- `FusionSettings` (core:model `signals/`): the 11 plan `phoneFusion` keys (`PlanBounds.FUSION_DEFAULTS`), `RANGES` per key (default, min, max), `clean` (unknown key dropped, clamp, equal-to-default dropped), `from(map)` -> `FusionParams`, `hash`. Defaults are derived from `FusionParams()` and PINNED by a test to the literal old numbers. Ranges are the plan's own `PlanBounds.fusionRange` (default +-50 %, fastKmh 20..40, fractions capped at 1.0), so a user setting can never leave what a plan may tune.
- Storage: `FusionSettings` lives in core:capture (next to `PlanBounds`, whose ranges it reuses). Phone prefs file `fusion_settings` (`FusionSettingsStore`, only non-default keys, cleaned on write and on load). Numbers only, no memory content: a per-device SETTING like `window_tolerance` (kept by Delete all, untouched by Forget), excluded from backup/transfer (`backup_rules.xml`, both sections of `data_extraction_rules.xml`, `BackupRulesTest`). The hub's base params stay `FusionParams(watchTtlMs = 1_500_000)` (today's effective defaults); the 11 keys are applied over them.
- `ContextHub` takes an `overrides` StateFlow; a change is a command on its actor that rebuilds the `ContextFusion` from the retained evidence (the same `rebuild()` a source change uses; hysteresis restarts from UNKNOWN = today's behaviour while evidence refills). No restart.
- UI: Signals page card "Phone fusion": per key 5 presets (min, between, default, between, max) plus a stored custom value, "Back to defaults". Logging: `fusion settings saved` (no values).
- Activity states stay STILL/WALKING/VEHICLE on the glasses; fusion output states are untouched.

### Item 3: Sensor recording (developer mode only)
Facts found: (a) the existing trace stores `g`/`a` events at the classifier's own rate (FULL/STILL 20 Hz/LOW 10 Hz, battery policy) and REPLAY feeds them to the classifier, so recorded raw data must NOT go into a trace. (b) There is no live radio transfer of traces today: the phone intake is `LaterSeams.noTraceIntake` (Task 18 not built); traces leave the glasses by the hand-over pull of `files/imu/traces/` (`tools/trace-pull.sh`). So "reuse the trace transfer path" = same directory root, same chunk codec (`TraceChunk` kind `sensor`), same pull, same deletion epoch/forget plumbing; NO new radio pattern.
- Setting: additive `HudSettings.sensorRecHz: Int = 0` (0 off, 5, 10, 25; `normalized()` snaps anything else to 0, so a hostile or old value is off). PROTOCOL_VERSION 1; old glasses ignore the key. Phone UI row in Settings > Diagnostics, visible only when developer mode is on; with developer mode off the phone writes 0 (`DeveloperModeStore` listener) so the value cannot linger.
- Glasses `SensorRecorder` (new, `glasses/.../capture/trace/`): REVISED after Codex review 1: it owns NO sensor registration. It is a read-only `SampleTap` on the classifier (the same mechanism the trace recorder and the shadow runner use), so it sees only the samples the existing `SensorFeed` already delivers at the rate the policy picked; the effective rate is min(chosen, delivered). `SensorFeed`, `MotionClassifier`, the rate policy and every capture decision are unchanged (no pin moved) and never read recorder state. Buffers samples in memory (bounded), flushes a BATCH every 60 s or 2,000 samples to `files/imu/sensor_rec/s-<startWallMs>-<endWallMs>-<seq>.json` (one `TraceChunk` JSON, gzip+base64+sha256 via `ChunkCodec`, kind `sensor`; no manifest, so `traces/` import and replay never see it). Writes go through the trace writer thread (same executor as wipe/forget), so wipe and write are ordered.
- Bounds: store cap 16 MiB total, oldest batch pruned first; a batch is at most one chunk file; no write when free space is under the trace floor (64 MiB).
- Deletion: `TraceStorage.wipe()` (new epoch = Forget all / Delete all) also deletes `sensor_rec/`; `runForget` ranges delete every batch whose [start,end] wall interval overlaps (file name carries the interval; an unparsable name is deleted). Backup: glasses `allowBackup=false` already; `data_extraction_rules`/`backup_rules` get `sensor_rec` explicitly excluded (test). Phone side stores nothing from this (no intake), so ResidueOracle has nothing to scan; a test pins that no phone store gets sensor data.
- Policy: records only while the Smart session runs AND capture is allowed (not paused, not parked/unworn, heat level not STOP, not low battery, not battery saver). No mark/photo exception (those exceptions exist only for a mark's own photo). Stops at once, buffer flushed (not discarded: it was recorded under policy).
- Logging by PcLog/DiagLog literals only: `sensor recording started`, `sensor recording stopped`, `sensor batch written`, `sensor batch pruned`, `sensor recording blocked` (no rates, counts or values).
- UI warning (phone, next to the rate): "records sensor data at X Hz and saves it in batches on the glasses (not sent to the phone yet; a developer pull reads it). Uses more battery." (the requested 'sends it in batches' would be untrue today, see Decision 2).

## Decisions (safe default chosen)
1. Try-it for derived signals is skipped (needs a second input editor); the expression box takes the graph JSON because the language has no text syntax.
2. Sensor recording batches stay on the glasses: there is no live trace transfer yet (phone intake is `noTraceIntake`) and `tools/trace-pull.sh` pulls `files/imu/traces` only, NOT `files/imu/sensor_rec`. The warning text says so instead of promising a transfer. To read the batches today: `adb exec-out run-as com.rokid.context.glasses tar -c -C files/imu sensor_rec` (each file is one `TraceChunk` JSON, kind `sensor`; decode with `ChunkCodec.decode(traceId, seq, sha256, b64)`). Choose: (a) extend `trace-pull.sh`/`handover.sh` to pull `sensor_rec` (small, tool only), (b) build the live `pc_trace_chunk` path (Task 17/18), or (c) keep as is. Safe default chosen: (c).
3. (revised) The recording registers nothing: no HAL rate change is possible. It records nothing in every state where `SensorRatePolicy.LOW_REASONS` applies (rest, battery_budget, phone_in_use, paused, not_worn, parked, heat, battery); in the calm STILL rate (20 Hz) it records at min(chosen, 20) because sampling continues there. Say if STILL should stop it too.
4. Presets 5/10/25 Hz; the sensors allow at least 50 Hz (classifier FULL uses SENSOR_DELAY_GAME), so 25 Hz is inside real capability.
5. Fusion ranges equal the plan's `PlanBounds.fusionRange` (default +-50 %), not wider.

## Policy (item 3, as built)
Recording runs only while ALL hold: a rate is set (Developer mode on, preset 5/10/25), a Smart capture session runs, capture is allowed (no pause, no quiet hours), the glasses are not parked, heat is not STOP, battery is not low (FrameGuard rule: <= low pct and not charging) and battery saver is off. No exception (the mark-photo exceptions belong to the mark's camera, not to a recording). On any blocker it stops within one 1 s beat and flushes what it holds. It does not close or start traces and is not in the trace settings hash.

## Codex review round 3 (2 Important, fixed; last round for this feature)
1. The cap check was check-then-increment, so two concurrent offers at cap-1 could both pass. Fix: `reserve()` is one compare-and-set loop (increment only below the cap) taken BEFORE the offer; the counter is decremented once per polled sample (and given back if making the sample throws), `take()` sizes its batch from what it polled, never from the counter. Tests: `twoConcurrentOffersAtCapMinusOneNeverExceedTheCap` (barrier seam: both threads read cap-1, only one takes the slot), `theCounterStaysWithinZeroAndTheCapUnderStress` (3 tap threads against poll/eligibility/flush), `aThrowInTheTap...` (+ slot given back). Mutations: plain increment after the check (fails), no decrement per polled sample (4 tests), no give-back on a throw.
2. A tap callback that read the old eligibility could offer after the drop, and a batch could be queued before a pause. Fix: every sample carries the generation the tap read BEFORE it read eligibility; `setEligible` (on every change) and `discard` bump the `AtomicLong` generation after the volatile write; `take()` discards samples whose generation is not current (so `configure(0)` flushes only current-generation samples) and the writer thread rejects a batch whose generation moved. Tests: `aBatchQueuedBeforeAPauseIsNotWrittenAfterIt`, `aCallbackPastTheEligibilityCheckThatOffersAfterTheDropIsNeverFlushed` (seam holds the tap after its eligibility read), `aSampleOfTheCurrentGenerationIsStillWritten`. Mutations: take ignores the generation, no bump on eligibility change, generation read after the window, writer ignores the generation.

# v0.9.7 slice B handoff: derived-signal editor, phone fusion thresholds, sensor recording (branch feat/v097-signals-b, base 2d2374c1)

## Design

### Item 1: Settings editor for derived signals (phone Compose, Settings > Capture > Signals)
- The expression IS the existing graph JSON (the language has no text syntax; the canvas JS stays untouched, `jsUnderSizeBudget` 4668 has no spare). The editor holds: a name field and a multi-line expression box with the graph JSON.
- Live validation = `DerivedSignals.validate(name, graph, current config)`, the very function `SignalConfigStore.saveDerived` (so `PUT /api/signals/derived/<name>`) calls. A JSON that does not parse is its own first problem. The first problem is shown; Save is disabled while any problem exists or the name/expression is empty.
- Save calls `SignalConfigStore.saveDerived` (no second write path), so the bounded 16-entry history, `remember`, wipe and logging by event name are inherited unchanged; replay of frozen versions is unchanged. Editing an existing signal loads its definition; delete stays as today. Shadow/trial only: nothing about liveability changes.
- Try-it: `ExprTry.run` needs per-signal series and a role; it cannot cheaply be driven from a one-line form without a second input editor. SKIPPED (Decision 1).

### Item 2: Phone fusion thresholds
- `FusionSettings` (core:model `signals/`): the 11 plan `phoneFusion` keys (`PlanBounds.FUSION_DEFAULTS`), `RANGES` per key (default, min, max), `clean` (unknown key dropped, clamp, equal-to-default dropped), `from(map)` -> `FusionParams`, `hash`. Defaults are derived from `FusionParams()` and PINNED by a test to the literal old numbers. Ranges are the plan's own `PlanBounds.fusionRange` (default +-50 %, fastKmh 20..40, fractions capped at 1.0), so a user setting can never leave what a plan may tune.
- Storage: phone prefs file `fusion_settings` (`FusionSettingsStore`, validated on write and load, like `SignalConfigStore`); user config -> wiped by Delete all (registered in `DeletionGraph.PREFS`, `MemoryWipe.WIPED_PREFS`), untouched by Forget, excluded from backup/transfer.
- `ContextHub` takes `paramsProvider`; the hub rebuilds `ContextFusion` with the new params when the stored values change (on its actor, no restart; the fusion keeps its state only through `reset`, which is fine: UNKNOWN = today's behaviour while evidence refills).
- UI: Signals page card "Phone fusion": per key 5 presets (min, between, default, between, max) plus a stored custom value, "Back to defaults". Logging: `fusion settings saved` (no values).
- Activity states stay STILL/WALKING/VEHICLE on the glasses; fusion output states are untouched.

### Item 3: Sensor recording (developer mode only)
Facts found: (a) the existing trace stores `g`/`a` events at the classifier's own rate (FULL/STILL 20 Hz/LOW 10 Hz, battery policy) and REPLAY feeds them to the classifier, so recorded raw data must NOT go into a trace. (b) There is no live radio transfer of traces today: the phone intake is `LaterSeams.noTraceIntake` (Task 18 not built); traces leave the glasses by the hand-over pull of `files/imu/traces/` (`tools/trace-pull.sh`). So "reuse the trace transfer path" = same directory root, same chunk codec (`TraceChunk` kind `sensor`), same pull, same deletion epoch/forget plumbing; NO new radio pattern.
- Setting: additive `HudSettings.sensorRecHz: Int = 0` (0 off, 5, 10, 25; `normalized()` snaps anything else to 0, so a hostile or old value is off). PROTOCOL_VERSION 1; old glasses ignore the key. Phone UI row in Settings > Diagnostics, visible only when developer mode is on; with developer mode off the phone writes 0 (`DeveloperModeStore` listener) so the value cannot linger.
- Glasses `SensorRecorder` (new, `glasses/.../capture/trace/`): its OWN `SensorEventListener` and thread (a second registration of gyro and linear acceleration at the chosen rate, software down-sample); `SensorFeed`, `MotionClassifier`, the rate policy and every capture decision are not touched and never read recorder state; the recorder reads no classifier state. Buffers samples in memory (bounded), flushes a BATCH every 60 s or 2,000 samples to `files/imu/sensor_rec/s-<startWallMs>-<endWallMs>-<seq>.json` (one `TraceChunk` JSON, gzip+base64+sha256 via `ChunkCodec`, kind `sensor`; no manifest, so `traces/` import and replay never see it). Writes go through the trace writer thread (same executor as wipe/forget), so wipe and write are ordered.
- Bounds: store cap 16 MiB total, oldest batch pruned first; a batch is at most one chunk file; no write when free space is under the trace floor (64 MiB).
- Deletion: `TraceStorage.wipe()` (new epoch = Forget all / Delete all) also deletes `sensor_rec/`; `runForget` ranges delete every batch whose [start,end] wall interval overlaps (file name carries the interval; an unparsable name is deleted). Backup: glasses `allowBackup=false` already; `data_extraction_rules`/`backup_rules` get `sensor_rec` explicitly excluded (test). Phone side stores nothing from this (no intake), so ResidueOracle has nothing to scan; a test pins that no phone store gets sensor data.
- Policy: records only while the Smart session runs AND capture is allowed (not paused, not parked/unworn, heat level not STOP, not low battery, not battery saver). No mark/photo exception (those exceptions exist only for a mark's own photo). Stops at once, buffer flushed (not discarded: it was recorded under policy).
- Logging by PcLog/DiagLog literals only: `sensor recording started`, `sensor recording stopped`, `sensor batch written`, `sensor batch pruned`, `sensor recording blocked` (no rates, counts or values).
- UI warning (phone, next to the switch): "Records sensor data at X Hz and saves it in batches on the glasses (pulled with the developer hand-over). Uses more battery."

## Decisions (safe default chosen)
1. Try-it for derived signals is skipped (needs a second input editor); the expression box takes the graph JSON because the language has no text syntax.
2. Sensor recording batches stay on the glasses until the existing pull: there is no live trace transfer yet (phone intake is a stub). The warning text says so instead of promising a radio transfer. If you want live batches over `pc_trace_chunk`, Task 17/18 must be built first.
3. Recording is a second sensor registration; the classifier listener is untouched, but the Android sensor HAL may run the sensor at the higher of the two requested rates. This only adds samples to the classifier's own listener if the HAL does not rate-limit per client; to be checked on the device (battery and classifier-rate log lines) before enabling for a wear day.
4. Presets 5/10/25 Hz; the sensors allow at least 50 Hz (classifier FULL uses SENSOR_DELAY_GAME), so 25 Hz is inside real capability.
5. Fusion ranges equal the plan's `PlanBounds.fusionRange` (default +-50 %), not wider.

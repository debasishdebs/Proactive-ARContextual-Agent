## 2. Decisions (binding for this part)

D1. **Two principals, two URL namespaces.** Helper principal: `/api/helper/*` only. Browser principal: everything else under `/api/` (including `/api/helper-jobs/*` and `/api/helper-status`). The router picks the principal from the path **before** dispatch. A helper token on a browser route is 401; a browser token on a helper route is 401. Neither token type is ever accepted for the other's routes, so granting a helper never grants browser authority.
D2. **Helper pairing code is minted only in the native app** (never by an HTTP route, never by a browser). 6 digits, **2 minutes** (browser code stays **5 minutes**: the browser flow needs a human to read, type, accept the certificate warning; the helper flow is typed right after the fingerprint check, so the shorter window narrows guessing time). Same lockout machinery (P2), separate counters and separate "New code" state per principal.
D3. **Tokens live in memory only** (SHA-256 compare in constant time, 32 random bytes, URL-safe base64). A process restart revokes them and aborts open jobs (consistent with `markRunningAborted`). One helper session at a time; a new pairing replaces the old one (`sessionGen` + 1, old session's open jobs voided). Idle 5 min without a poll, max age 12 h.
D4. **Capability grants** `py_exec` and `promote`: two independent switches in a native Compose card, stored in SharedPreferences `canvas_helper_grants`, **both off initially**, excluded from backup, never restored. They are checked live at every poll, lease, heartbeat and result (not baked into a token). Turning one off voids that capability's open jobs.
D5. **Which jobs need what.**
 - `py_exec` (experiment-only Python): needs grant `py_exec`. Created **only in-process** by `PythonExecutor` during a canvas run (so provenance is exact); the browser cannot submit it. No per-job confirmation (the grant is the consent; the container has no network). Open question Q1 asks whether the user wants a per-job confirmation anyway.
 - `tool_build`: needs grant `promote` **for leasing and for result submission**, plus one **native confirmation per job** (D6). Submitted by the browser (`POST /api/helper-jobs`), parked in `AWAITING_CONFIRM`.
D6. **Native confirmation** = an in-process call from a Compose card (no HTTP route exists for it). It stores `confirmHash = HMAC-SHA256(processSecret, jobId | bundleHash | sessionGen | expiresAtMs)` and `confirmExpiresAt` (5 min). Lease re-derives the HMAC; any change of bundle, session or expiry fails. `processSecret` is 32 random bytes held in memory only, so neither browser nor helper credentials can mint it, and a restart voids pending confirmations.
D7. **Frozen bundle.** `bundleHash = sha256(canonical(payload))` (keys sorted, no whitespace, UTF-8) is computed by the phone at submit from the stored `payloadJson`; the payload column is write-once (no DAO update of it). The helper recomputes the hash over the bytes it receives and refuses a mismatch. The confirmation card shows the first 12 hex characters.
D8. **Persistence** is inline in Room (inside the SQLCipher database, which backup rules already exclude): `payloadJson` (cap 1 MiB) and `resultJson` (cap 2 MiB) are columns of `canvas_helper_job`, not files, so Delete all and Forget remove them with the row and no new files enter the deletion inventory. Cleanup commands live in a **new table that is not wiped** (opaque ids only, no user data).
D9. **Lease 10 s; heartbeats on a fixed 1 s schedule (not waiting for the previous answer, request timeout 1 s, at most 2 in flight); the helper's liveness deadline is `helperSelfKillMs` = 3.5 s counted from the monotonic SEND time of the last acknowledged request (never from the time the ack arrived); watchdog tick 100 ms, scheduling slack 300 ms, kill budget 1 s => 3500 + 100 + 300 + 1000 = 4900 ms, at most 5 s from the deletion event to a dead container while the helper process is alive** (section 3.4, master R1; one lost beat is tolerated, two are not guaranteed). If the helper process itself dies, the bound is the container's runtime deadline and the helper restart (no VM-side watchdog: master R1/Q12). The old 60 s lease is dropped. A lease that expires FAILS the job (`lease_expired`); there is no automatic re-lease (the user resubmits). So no two helpers can ever run one job.
D10. **First release is ASYNC-only experiments.** `py.fn` and `tool.draft` are ASYNC-domain nodes that run only in `CanvasRunner` experiments. Deferred (not in this plan): RT replay lockstep with Python, Python in sweeps, fusion tunables (refused until 3a Task 13: pinned by P17), LIVE (refused until 3a Task 25: pinned by P17), second CLI/runtime, rich editor, promotion to Kotlin. 3a's pulled-trace import (`TraceImport`, Task 19) stays the only trace source (Tasks 17/18 absent).
D11. **Deletion fences before the first executable job.** P9 lands before P11 (the lease route) and before P16.
D12. **No sensing change.** `py.fn` and `tool.draft` are ASYNC nodes, so the capture-plan compile ignores them; P17 pins that the compiled `configHash` of a graph is identical with and without a `py.fn` node.

### 3.3 Endpoints (all JSON; `{job}` ids match `^[A-Za-z0-9:_-]{1,64}$`)
1. `POST /api/helper/pair` (no auth; helper lockout) body `{"helperProtocol":1,"code":"123456","name":"<=40 chars"}`
   - 200 `{"token","helperId","sessionGen":int,"caps":{"py_exec":bool,"promote":bool},"constants":{...}}`
   - 400 `bad_request`; 409 `protocol_mismatch`; 401 `unauthorized` with `triesLeft` (wrong code) or the no-code text; 429 `refused` with `Retry-After` (locked; only the native "New code" reopens after the global lock).
2. `POST /api/helper/poll` body `{"helperProtocol":1,"active":[{"jobId","leaseGen":int}],"cleanupAcks":["<cleanupId>"]}`
   - 200 `{"sessionGen","caps":{...},"serverTimeMs","available":["py_exec","tool_build"],"cancel":["<jobId>"],"cleanup":[{"cleanupId","jobId":"<id>|*"}]}`
   - `available` lists only the job types that are queued **and** whose grant is on (and, for `tool_build`, confirmed). `cancel` lists jobs the helper reported in `active` that are no longer leased to it. `cleanup` repeats until acked. 401 means the session is gone: stop everything (3.4).
3. `POST /api/helper/lease` body `{"helperProtocol":1,"types":["py_exec","tool_build"]}`
   - 200 `{"job":null}` or `{"job":{"jobId","type","leaseGen":int,"leaseUntilMs","deadlineMs","bundleHash","payloadBytes"},"serverTimeMs":int}` (`leaseUntilMs` and `deadlineMs` are absolute phone-clock ms; the helper converts to a local monotonic deadline with `serverTimeMs`, never with its own wall clock; a second lease while one is held returns `{"job":null}`)
   - 403 `capability_revoked` when every requested type is ungranted.
4. `GET /api/helper/jobs/{job}/payload?leaseGen=N` -> 200 the exact stored payload bytes (the helper hashes them and compares to `bundleHash`); 409 with a code from 3.5. **Payload release is transactional (round 1, finding 2):** the DAO re-checks the job state, the deletion fence and the frame-Forget revision (3.4a) in the same transaction that reads the payload column; if a frame carried by the job was forgotten the job is voided there and the answer is `409 voided` with no body.
5. `POST /api/helper/jobs/{job}/heartbeat` body `{"leaseGen":N,"progress":{"done":int,"total":int}}` (progress optional) -> 200 `{"leaseUntilMs","serverTimeMs"}`; otherwise 401/403/404/409 (3.5). The phone answers 200 only if, **inside the DAO transaction that renews the lease**, the job is `LEASED` to this helper and generation and no frame, trace or wipe deletion has happened (3.4); it never acks after a deletion event.
6. `POST /api/helper/jobs/{job}/result` body `{"leaseGen":N,"resultHash":"<sha256 hex of canonical result>","result":{...}}`
   - 200 `{"committed":true,"duplicate":false}`. A **retry of the same (jobId, leaseGen, resultHash)** after a lost response gets 200 `{"committed":true,"duplicate":true}` and changes nothing.
   - 409 (3.5), 413 `too_large`, 422 `invalid_result` (schema), 403 `capability_revoked` (`promote` or `py_exec` turned off after lease: the job is voided).
7. `POST /api/helper/jobs/{job}/fail` body `{"leaseGen":N,"code":"needs_runtime|timeout|oom|guard_rejected|runtime_error|no_cli|killed|bad_output|too_large|resources_busy|disk_low|gen_unavailable|gen_auth_failed|no_key|toolchain_mismatch"}` -> 200 `{"ok":true}` or 409 (3.5). Codes are an enum; no free text.

Browser-side routes (`/api/helper-jobs`, `/api/helper-status`) are phone-internal and not part of this contract.

### 3.4 Kill policy and the deletion-to-death timing contract (explicit, <= 5 s while the helper process is alive)
**Definitions.** `T_del` = the instant the phone commits a deletion-class event (cancel, void, Forget, Delete all, grant off, session end, expiry). `s_i` = the helper's **monotonic send time** of request `i` (heartbeat or the lease request that started the job). The helper keeps `anchor = s_i` of the **last request that returned 2xx**; the arrival time of that answer is never used. Because the phone only answers 200 to a request it processed before `T_del` (and processing happens after `s_i`), `s_i <= (processing instant) <= T_del` for every ack that can exist; a late-arriving ack of a request sent before the deletion can therefore only **shorten** the helper's remaining time, never extend it (the old rule "4 s since the last ack" let an ack that was processed before the deletion but delivered after it restart the timer).
**Schedule.** Heartbeats are sent every `heartbeatIntervalMs` = 1000 ms on a fixed timer, independent of whether the previous request has finished (at most 2 in flight), each with a hard `heartbeatRequestTimeoutMs` = 1000 ms. The liveness deadline is `anchor + helperSelfKillMs` (3500 ms). **One lost beat is tolerated:** if the beat sent at `anchor + 1000` is lost, the beat sent at `anchor + 2000` is answered no later than `anchor + 3000` (1000 ms timeout), inside the 3500 ms window; **two consecutive lost beats are not guaranteed to survive** (the beat sent at `anchor + 3000` could only be acked after the deadline). This is a deliberate trade: a longer window would break the 5 s bound.
**Budget (all of it is in the 5 s).** `helperSelfKillMs` 3500 + `watchdogTickMs` 100 (the watchdog thread checks every 100 ms, so detection is at most 100 ms late) + `schedulingSlackMs` 300 (timer and scheduler lateness reserved) + `killBudgetMs` 1000 (kill by name, verify gone) = **4900 ms <= `maxKillLatencyMs` 5000 < `leaseMs` 10000**. The bound is from `T_del`, because `anchor <= T_del`. A denied heartbeat (401/403/404/409) kills at once (<= 1 s). Test `killBudgetArithmetic` pins the sum.
Supervision (heartbeats, polling, watchdog) runs **independently of the runner and of every other network call** (separate thread or process; a blocked runner, a blocked poll or a blocked result POST must not delay the watchdog; every network call has a hard timeout and the watchdog never waits on a network call). Kill the job's container by name (and label sweep) when any of these holds:
- a heartbeat answer is 401, 403, 404 or 409 (any code in 3.5), or a poll answers 401 (token revoked, session gone, LAN off, Forget, Delete all): kill at once;
- `now_monotonic > anchor + helperSelfKillMs` (phone unreachable, LAN lost, timeouts, 5xx, 429, a result POST that hangs the helper's own network stack): kill, then verify gone within `killBudgetMs`;
- the lease deadline `deadlineMs` passes locally (converted with `serverTimeMs`; never the wall clock);
- the container runtime's own per-run deadline fires (defence in depth: each container's runtime deadline is `min(profile deadline from part-A table 6, remaining job deadline) + 2 s`);
- on helper start, any container with the helper's label is an orphan: kill it before polling.
**Honest scope of the guarantee (round 1, finding 3; master R1).** The 5 s bound holds **while the helper process is alive** (including when the phone is unreachable or never answers). If the helper process dies, is `kill -9`ed or the Mac sleeps, no process remains to enforce the 3.5 s rule; the container then ends at its runtime deadline (`py_exec` job deadline + 2 s, at most 132 s; `gen` 15 min + 2 s; `verify` the sequence cap + 2 s) or at the next helper start (orphan kill before the first poll), and the phone-side lease (10 s) fails the job and enqueues the cleanup command meanwhile. **No VM-side liveness watchdog is built** (it costs about 2.5 agent-h plus a live gate, more than the 2 h the review allowed, and adds a second process that must itself be supervised); the narrower guarantee is stated in the UI, the release notes and the checklist. Q12 in the master asks whether to buy the watchdog.
**Required tests (named; part C H3a/H3b implement the helper half, P14 the phone half):** `delayedPreDeletionAckDoesNotExtendLiveness` (request sent at `t0`, deletion at `t0+100`, the 200 delivered at `t0+900`: the helper still dies by `t0 + 3500 + 100 + 300 + 1000`), `oneLostBeatToleratedTwoNot`, `blockedPollDoesNotDelayKill`, `blockedResultPostDoesNotDelayKill`, `watchdogTickAndSlackInsideBudget`, `noAckFor35sKillsWithin5s`, `helperProcessDeathLeavesContainerToRuntimeDeadline` (live H13: `kill -9` the helper, the container is gone at its runtime deadline or at the next helper start, and this narrower behaviour is the asserted one).
After a **deletion-class** denial (`voided`, `cancelled`, `capability_revoked`, `not_found`, 401) the helper deletes every laptop copy of that job (inputs, outputs, logs) immediately and does not post a result. After `lease_expired` or `deadline_exceeded` it deletes inputs and keeps nothing it cannot report. Cleanup commands from `poll` (`cleanup[]`) are executed even for unknown job ids; `jobId:"*"` means all jobs (Delete all); ack by listing the `cleanupId` in the next poll's `cleanupAcks`. The phone re-sends until acked.

### 3.4a Frame provenance and the frame-Forget fence (round 1, finding 2)
`sourcesHold()` checks trace revisions and `labelRev`; an ordinary frame Forget changes neither, so a helper job could be inserted with a payload built from frames forgotten after the runner's pre-check. The fence is therefore extended and checked **transactionally at three points**:
- **Authoritative provenance.** The frame ids carried by a job are exactly the frames `PhotoSource` returned for the run (the `PhotoLoad` ids of the chunk), taken by `CanvasRunner`, never copied from a request body; they are stored in `frameIdsJson` and are what `voidHelperJobsForFrames` matches.
- **Frame-forget revision.** `canvas_meta` key `frame_forget_rev` (a counter, no new table) is bumped **in the same transaction** by every frame-level Forget path (`deleteLabelsForFrames`, the frame cascade of `CanvasSlice3Forget`, `forgetRangeTx`, `voidHelperJobsForFrames`, `WipeDao`). `CanvasRunner` captures `HelperFence(wipeGen, deletionEpoch, frameForgetRev)` **before it loads the inputs** (where it already captures `generation`) and passes it through `RunContext` to the executor and `HelperJobPort.runPy`.
- **Checks.** (1) Insertion (`insertHelperJobFenced`): wipe generation, epoch and `frame_forget_rev == captured` in the insert transaction, else refuse. (2) Lease/payload release (`leaseHelperJob`, payload GET): the job row's stored `frameForgetRev` still equals the current counter or the job is voided in that transaction (fail closed: a Forget of any frame voids in-flight helper jobs, which is acceptable because Forget is rare). (3) Result commit (`commitHelperResultFenced`): same check before the `UPDATE`. A job inserted before a Forget is also voided by `voidHelperJobsForFrames` (existing path), so the counter only has to close the gap before insertion and between release and commit. Named test (P7a/P9): `forgetBetweenRunnerPrecheckAndHelperInsertRefusesPayload` with a frame that has no labels and no trace sources.

### 3.6 Job payloads and results (fixtures in `protocol/samples/`)
- **py_exec payload** `{"helperProtocol":1,"jobType":"py_exec","profile":"py_exec","source":"<=16000 chars","entry":"run","items":[{"id":"i0","input":{...}}],"outSchema":{...},"limits":{"perItemMs":5000,"jobMs":120000}}`. ### 3.6a The shared contracts owned by P1 (round 1, findings 7, 8, 9)
All of these live in `tools/canvas-helper/protocol/` as data (P1 owns the folder), are read by **both** the Kotlin tests and the Python tests, and are the only definition; part C may not restate them.
1. **Schema subset (`schema-subset-v1.json`).** Keywords (exactly these, nothing else is accepted): `type` (`object|array|string|integer|number|boolean|null`), `required`, `properties`, `additionalProperties` (boolean only; **must be `false` on every object schema of a tool contract**), `enum`, `items` (one schema), `minimum`, `maximum`, `minLength`, `maxLength`, `minItems`, `maxItems`, `pattern`. There is **no** `maxDepth` keyword: the instance-depth cap is a validator constant `maxInstanceDepth = 8`. `pattern` supports only an anchored (`^...$`) subset: literals, escapes `\d \w \s \. \-`, character classes `[...]`, groups `(...)` without nesting, alternation `|`, quantifiers `? * + {m,n}` with `n <= 64`; no back-references, look-around or flags. A run that is suspended inside `PythonExecutor.run` therefore resumes with a `CancellationException`, `HelperJobPort.runPy` cancels the helper job (P10b), and the run ends `CANCELLED`; the item/run rows are written exactly as for a flag-based cancel (the `NonCancellable` commit block already used by the runner). A cancel arriving between chunks still ends the run before the next chunk starts (unchanged). A/B: cancelling A while A's chunk is suspended also cancels the job and B never starts; `cancelGroup` between A's end and B's start is unchanged.
- **Fence plumbing.** Where the runner captures `generation` before it loads the photos, it also captures `HelperFence` (wipe generation, deletion epoch, `frameForgetRev`) and the authoritative frame ids of the chunk, and exposes both to executors through `RunContext` (`ctx.helperFence`, `ctx.frameIds`), so `PythonExecutor` passes the fence captured **before the inputs were loaded** (3.4a). The executor never reads a fence of its own.
- **Waiters on every terminal state:** covered by P10b; this task tests it end to end through the runner.

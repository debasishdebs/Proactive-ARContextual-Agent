**Separation of supervision from execution (finding 4).** `supervisor.py` owns every network call (poll, heartbeat, result, ack) and holds the *only* handle that can kill a job. Execution (`runner.py`) runs container commands as subprocesses with their own timeouts and never makes a network call. The supervisor does not block on the runner; the runner cannot block the supervisor; **the liveness watchdog is its own thread that reads only a monotonic deadline variable and never waits on a network call** (a hung poll or a hung result POST cannot delay it). The explicit policy (all numbers are constants in `supervisor.py`, asserted by tests against `protocol/constants.json`; derivation in part B 3.4):

| Event | Action | Bound |
|---|---|---|
| Heartbeat schedule | a fixed 1.0 s timer (`heartbeatIntervalMs`) sends a beat for the one leased job whether or not the previous request finished (at most 2 in flight); each request has a hard 1.0 s timeout (`heartbeatRequestTimeoutMs`) | one lost beat is tolerated, two consecutive lost beats are not guaranteed to survive |
| Liveness anchor | on every 2xx answer set `anchor = monotonic SEND time of that request` (the lease request's send time for the first anchor); **never the arrival time** | an ack delivered after a deletion that was processed before it cannot restart the timer beyond `sendTime + 3.5 s` |
| Liveness deadline | kill when `monotonic_now > anchor + helperSelfKillMs` (3.5 s), checked by the watchdog thread every `watchdogTickMs` (100 ms); `schedulingSlackMs` (300 ms) is reserved for timer lateness | `3500 + 100 + 300 + 1000 = 4900 ms <= 5000` from the deletion event |
| Heartbeat answer 401/403/404/409 (any code in part B 3.5), `lease_expired` | kill container by name immediately | kill call timeout 1.0 s (kill budget `killBudgetMs` = 1.0 s) |
| Connection failure, timeout, 5xx or 429, a blocked poll or result POST | no 2xx ack: the liveness deadline above fires; nothing else is waited for | same 4.9 s |
| Local lease deadline `last_ok_monotonic + leaseMs` (10 s) or job `deadlineMs` (via the `serverTimeMs` offset) passes | kill | backstop; the 3.5 s rule fires first |
| Container wall deadline | runtime-enforced `podman run --timeout <min(profile deadline, remaining job deadline) + 2 s>` AND a supervisor timer; the timer is a backstop only | `deadlineS` from A-RES; **this is also the only bound if the helper process dies** |
| Kill itself fails | `rm -f` by name, then mark `cleanup_pending` in the journal and retry every 1 s | retried until gone |
| **Overall cancel-to-gone target** | **<= 5 s from the deletion event while the helper process is alive** (4.9 s budget); a denied heartbeat kills at once (<= 1 s) | tested with a fake clock (H3a/H3b) and live (H13) |
| **Helper process dies / is `kill -9`ed / the Mac sleeps** | **not covered by the 5 s guarantee** (round 1, finding 3; master R1): the container ends at its runtime deadline (`py_exec` <= 132 s, `gen` <= 15 min + 2 s, `verify` sequence cap + 2 s) or at the next helper start (orphan kill before the first poll); the phone's 10 s lease fails the job and queues the cleanup meanwhile | no VM-side watchdog is built (about 2.5 agent-h, Q12); asserted by live test `helperProcessDeathLeavesContainerToRuntimeDeadline` (H13) |

Orphan recovery (H4): every container is created with labels `pca.helper=<instanceId>` and `pca.job=<jobId>`; on helper start the journal and `podman ps -a --filter label=pca.helper` are reconciled: anything not in the journal as running, or whose helper process died, is killed and removed and its job dir deleted before the first poll; **orphan job filesystems** (`/var/lib/pca/jobs/*.img`, `/var/lib/pca/mnt/*` not belonging to a journalled running job) are unmounted and removed in the same pass.

**Network call bounds:** every helper HTTP call has an explicit connect/read timeout (1.0 s for heartbeat, <= 5 s for poll/result/ack; none of them is ever waited on by the liveness watchdog) and no unbounded retry loop; tests monkeypatch `socket` to hang and assert the timeout.

**No host fallback, one runtime (finding 5).** `runtime.py` does not search PATH for "podman else docker". It reads the **named connection** from `~/.pca-helper/config.json` (set by `setup`), inspects it (`podman system connection list`, `podman info --format json`: rootless true, expected machine name, expected socket, no extra host-share volumes outside the staging roots) and refuses anything else with `needs_runtime`. There is no `subprocess.run([python, ...job code...])` anywhere in the package, enforced by a source-grep test (`noHostExecutionPath`). Docker is not supported in this part (second runtime cut).

**Effective-isolation verification at execution (finding 5).** The runner uses `create`, then `podman inspect <name>`, then `start`. The inspection result must match the profile exactly (mounts set equals the profile's list and read-only flags, **the only rw mounts being the job's quota-limited VM filesystem paths of part-A 6.1**; `NetworkMode`; `ReadonlyRootfs`; `CapDrop` ALL; `SecurityOpt` contains no-new-privileges and does not contain `seccomp=unconfined`; `Privileged` false; `PidsLimit`, `Memory`, `MemorySwap`, `NanoCpus`; `User` non-root; no `--pid=host/--userns=host/--ipc=host`). Mismatch = remove the container, fail `needs_runtime`, never start. After start the supervisor also reads `podman stats --no-stream` once to check that memory and pids limits are applied (soft check, logged). Staging roots: the Podman machine is created with explicit `-v $HOME/.pca-helper/stage:/stage` only (the VM path is `/stage`; the runner rewrites every `-v` source to `/stage/<job>/...`, R9), and `doctor` fails if the machine shares `$HOME`. Escape via a kernel/runtime bug is NOT excluded by any payload test: stated in section 9.

**Host-side processing of generated data (finding 2).** Rules enforced by tests: (1) the helper never runs `git`, a generated script, a build or a formatter on anything the generator produced; the only `git` use in the package is `snapshot.py` against the user's *trusted* checkout at a fixed commit, before any job runs, with `GIT_CONFIG_NOSYSTEM=1 -c core.fsmonitor= -c core.hooksPath=/dev/null` and a source-grep test that no `git`/`subprocess` call takes a path under a job dir. (2) The diff is created INSIDE the gen container by the image-owned `gen_finalize.py` (difflib against the pristine template; no git) and emitted as `out/patch.diff` plus the two file contents; the host treats it as data and validates it (H19). (3) The patch is applied only inside the verify container, by the image-owned `verify_steps.py apply` (its own strict unified-diff applier limited to the two allowed paths) onto a **fresh copy of the read-only baseline snapshot**. (4) Outputs are exported from the quota-limited VM filesystem by trusted VM-side code (`pca-jobfs.sh export`, `cp -a --no-dereference`, free-space check first) only after the container is confirmed gone (`podman container exists` false) and are then validated by `collect.py` (H8) before any content is read. **No container ever has a writable mount that points at the Mac** (finding 1).

## 3. Gates and capability enabling (fixes the old T5b/T9a cycle, finding 14)

Capabilities are enabled by **gate stamps**, not by task order alone. `pca-helper gate <python|gen|verify>` runs that gate's live suite; on a full pass it writes `~/.pca-helper/gates/<name>.json` = `{suiteSha256, imagesLockSha256, helperVersion, podmanVersion, passedAt}`. At startup `gates.py` recomputes the first three inputs and the helper advertises capability `py_exec` only with a valid `python` stamp, `tool_build` only with valid `gen` AND `verify` stamps. Any change to the suite files, `images.lock`, or the profile table invalidates the stamp (test `stampInvalidatedByProfileChange`). The `python` stamp needs H13a **and** H13b; the `gen` stamp needs H22 (which includes the S1b malicious-fixture re-run); the `verify` stamp needs H27a **and** H27b (hostile fixtures). Order: gate python before py.fn is enabled; gate gen (H22) is implemented together with its proxy and profile (H20, H21) and never depends on later tasks; gate verify likewise. Every live suite runs through `pca_lock.py` (L1). Hashes in the stamp also cover `config/gen_cli_flags.json`, `config/test-heap.init.gradle` and `protocol/generated-files.json`. Part-B's fences (B-FENCE) must exist before the first stamp is created for real on a device (milestone rule M1 below).

**H11 In-container harness `pyjob_entry.py`: an external per-item watchdog** (2.5 h; deps H10; round 1, finding 14)
Files: `container/pyjob_entry.py` (+ copies `schema_lite.py` at image build), `tests/test_pyjob_entry.py` (runs locally under plain Python as a unit; isolation is the container's job).
**Why the old design failed:** a `signal.setitimer`/alarm handler runs in the same process as the user's source, which can replace the handler, ignore the signal or catch the exception, so the 5 s item limit was cooperative. **New boundary:** `pyjob_entry.py` is the trusted parent and **PID 1 of the container** (no user code runs in it; signals sent to PID 1 from inside its own PID namespace cannot kill or stop it). It reads `/in/inputs.json` and `/in/fn.py` (<= 16,000 chars, checked), and runs **each item in a fresh child process in its own session** (`subprocess.Popen([sys.executable, worker.py, item], start_new_session=True)`; the worker imports the user's source and calls `run`; the item input and the bounded output cross a pipe). The parent enforces the per-item limit (`perItemS` from A-RES, 5 s) with its own monotonic timer: on expiry it `SIGKILL`s the item's whole process group, then sweeps `/proc` for any remaining process of the container's uid other than itself and kills it (so a `setsid`, double-fork or spawned child cannot outlive its item), and records the item as `timeout`. It reads at most `maxItemOutputBytes` from the pipe (else `too_big`), validates each output against the out schema (`schema_lite`) in the parent, writes `/out/out.json` with per-item `{ok, code}`; error codes are the part-B 3.6 item codes (`timeout, schema_mismatch, exception, too_big`; R11), never a traceback or path. The job-level `--timeout` of the container remains the outer backstop.
RED: `schemaMismatchFailsItem`, `timeoutFailsItemNotJob`, **`caughtAlarmDoesNotDefeatTimeout`** (user code installs a `SIGALRM` handler, wraps itself in `try/except BaseException` and loops: the item still ends `timeout` at the limit), **`ignoredSignalsDoNotDefeatTimeout`** (`signal.signal(SIGTERM/SIGALRM/SIGINT, SIG_IGN)`, then `time.sleep(60)`), **`stoppedWorkerStillTimesOut`** (`os.kill(os.getpid(), SIGSTOP)`), **`spawnedChildrenKilledWithItem`** (user code `subprocess.Popen(["sleep","60"])` and `os.fork()`; after the item no child remains: `/proc` scan count 0), `exceptionBecomesCodeNoTraceback`, `oversizeOutputFailsItem`, `onlyFixedCodesEmitted`, `parentHasNoUserCodeImport` (grep: the parent module never imports the user source), `nextItemRunsAfterTimeout`.

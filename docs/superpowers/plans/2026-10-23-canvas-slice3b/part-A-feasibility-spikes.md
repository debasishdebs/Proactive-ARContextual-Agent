## 0. Global rules for all spikes
- Never print or log secrets. Evidence is counts and names only (hostnames, byte counts, exit codes, file counts, SHA-256 of build outputs, versions). The key file is read only by the helper process; spikes run `canary-scan` (section 0.1) instead of grepping for the key.
- No host-run fallback ever: if a container step cannot run, the spike fails; it never runs the CLI, Gradle or generated code on the Mac.
- **One named rootless Podman connection (round 1, finding 11).** `podman machine init` creates both a user connection and a `-root` connection, so "exactly one row" is a false failure. Preflight (run at the start of every spike and by helper `doctor`): `podman system connection list --format json` must contain the configured name `podman-machine-default` with `Default == true`, a user-level URI (path under `/run/user/`, never the `-root` connection) and the configured connection must be the one `podman` uses (`podman info --format '{{.Host.Security.Rootless}}'` prints `true`); the `-root` row may exist and is never used. `podman machine inspect --format '{{.Rootful}}'` expects `false`.
- Not allowed: `--privileged`, `--net=host`, any socket mount, any mount of `~/.claude`, `~/.codex`, `~/.ssh`, `~/.gradle`, the repo checkout, or `$HOME`. Allowed host paths are only `~/.pca-helper/stage/<job>/...`; inside the VM that tree is `/stage/<job>/...`, and **every `-v` source in a `podman run` is the VM path `/stage/...` or a VM-local job filesystem path `/var/lib/pca/mnt/<job>/...`** (master plan R9, R21).
- **Untrusted code never gets a writable mount that points at the Mac** (round 1, finding 1). Every directory that container code can write is a VM-local, kernel-limited filesystem (section 6.1); the Mac stage tree is mounted read-only into containers and receives data only through the post-termination export (section 6.1).
- **One lock protocol (round 1, finding 6, master R12).** Every VM-heavy, VM-light and host Gradle command in this plan, in every spike and task, is started through `tools/canvas-helper/pca_lock.py <host-build|vm-light|vm-heavy> -- <command>` (deliverable of L1). A command that is run without it is not valid evidence.
- No machine-wide `pkill`/`killall`/`gradle --stop`; teardown is by container/volume/network name.
- Each spike writes its result to `docs/superpowers/plans/2026-10-23-canvas-slice3b/phase0-evidence.md` (future file, one section per spike, PASS/FAIL line first). No other file is edited by the spike apart from the reusable artifacts named in its "Deliverable".
- **RED then GREEN then mutation for every spike (round 1, finding 15).** Each spike first writes its check script (`spikes/<id>_check.sh` or `.py`: one line per expected result, `PASS`/`FAIL`) and runs it against the not-yet-built environment: it must print `FAIL` for every line (RED, recorded in the evidence). It is run again after the setup (GREEN). Then the spike's **named mutation** is applied, the check is re-run and the named check must turn `FAIL`, then the mutation is reverted and the check is `PASS` again. Named mutations are listed in each spike.
- **Re-estimate trigger (applies to each):** at 60 % of its cap the implementer posts a one-line status; at the cap it stops, writes the evidence so far, and the controller decides (continue only with a new written cap, or take the fallback). A fixed fail result ends the spike immediately; no third attempt at the same step.

## 2. Spike group S2: enforced isolation on this Mac (L1 + S2a + S2b + S2c, cap 7.5 agent-h; do first)

**Goal.** Prove, with commands and expected output, a topology where the generation container can reach **only** an allow-list proxy: no direct IPv4/IPv6, no external DNS, no host/LAN services, no runtime API socket, no home share; the proxy permits exact API hosts on port 443 only, refuses private destinations, and fails closed; and prove that every directory untrusted code can write is a **kernel-limited (bytes and inodes) VM filesystem**, not a Mac bind mount watched by a poller. Replaces the unsafe "normal network plus HTTPS_PROXY" idea (Codex #1) and the default home share (Codex #5).

**Topology (decided).**
- `pca-int`: `--internal` network, fixed subnet 10.89.77.0/24, DNS disabled (no resolver reachable, no gateway). Gen and probe containers attach **only** here.
- `pca-egress`: ordinary bridge 10.89.78.0/24 with outbound NAT.
- `pca-proxy`: the only container on both (`pca-int` at fixed IP 10.89.77.2, plus `pca-egress`). Gen uses `HTTPS_PROXY=http://10.89.77.2:3128` (IP, not a name, so no DNS is needed). The proxy is a container, so **nothing listens on the Mac** and the old "helper never binds/listens" test stays true.
- Proxy behaviour (stdlib asyncio CONNECT-only, about 100 lines, becomes part-C `pca_helper/proxy.py`): allow-list file mounted read-only; accepts only `CONNECT <exact-host>:443`; resolves the host itself and requires **every** resolved address to satisfy `ipaddress.ip_address(a).is_global` (rejects private, loopback, link-local, ULA, multicast, 169.254/16); connects to the resolved IP (no re-resolution); max 4 concurrent tunnels, 10 MiB per tunnel per direction, 300 s tunnel cap; logs one line per request: UTC time, host, port, verdict, bytes (no path, no headers); empty or unreadable allow-list means exit non-zero at start (fail closed); any exception means connection closed, never forwarded.
- Proxy container flags: `--read-only --cap-drop=ALL --security-opt no-new-privileges --pids-limit 64 --memory 128m --memory-swap 128m --cpus 0.5 --tmpfs /tmp:size=16m --user 10001`, no published ports.

**Preconditions.** Opera closed (gate above). `podman` 6.1.4. Pinned base image digest for the probe and proxy: `docker.io/library/python:3.12-slim` (record `podman image inspect --format '{{.Digest}}'` into `images.lock`). No key file is needed for S2 (the allowed-host positive control sends no credentials). The user approves removing the empty machine and, for the job filesystems (S2c), the VM-internal `sudo mount` of loop images (open question 4).

### 2.0 L1: shared lock launcher (1.5 agent-h, Python, no Podman; deliverable first)
**Deliverables.** `tools/canvas-helper/pca_lock.py` (stdlib, importable library and CLI), `tools/with-build-slot.sh` (a shim of at most 5 lines: `exec python3 "$(dirname "$0")/canvas-helper/pca_lock.py" host-build -- "$@"`; **no lock logic in shell**), `tools/canvas-helper/tests/test_pca_lock.py`. macOS has no `flock` binary; Python's `fcntl.flock` is the only mechanism, used by every entry point.
**Protocol** (all locks are files in `~/.pca-helper/run/`, `0600`, created on demand, **never** inside a repo or worktree; every acquisition is non-blocking and fails with exit code 75 and the text `resources_busy`; a caller may retry with its own timeout outside the lock; the kernel releases an flock when its holder dies, so a SIGKILLed holder never leaves a stale lock; owner pid/name files `*.owner` are informational only):
- `heavy.lock`: **host builds hold it shared** (`LOCK_SH`); `vm-heavy` jobs (S3a/S3b, `setup`, `verify`, H27a/b, H28 live) hold it **exclusively** (`LOCK_EX`). The kernel arbitrates, so there is no check-then-take race: a simultaneous host build and heavy VM job cannot both succeed.
- `host-slot-1.lock`, `host-slot-2.lock` (`LOCK_EX`): a `host-build` takes `heavy.lock` shared, then slot 1, else slot 2 (host concurrency 2). After taking slot 2 it checks `podman machine list --format '{{.Running}}'`; if the VM is up it releases slot 2 and refuses (so VM up and idle still allows one host build).
- `light.lock` (`LOCK_EX`): one `vm-light` job at a time (S2c, S1a/b, H13, H22, gen, py_exec). A `vm-light` job also takes `host-slot-2.lock` for its lifetime, so **while a light VM job runs at most one host build exists**; it refuses to start when slot 2 is held by a host build or when `heavy.lock` is exclusively held. Any command that starts the VM (`podman machine start`) goes through `vm-light` or `vm-heavy`, never directly.
- Lock order is fixed (`heavy.lock`, then `host-slot-2`, then `host-slot-1`, then `light.lock`), every acquisition is non-blocking, so there is no deadlock.
- The resulting table is master section 6.2 (VM stopped: 2 host builds; VM light job: 1; VM heavy job: 0).
**RED tests (named):** `simultaneousHeavyAndHostBuildExactlyOneWins` (two processes released by a barrier, repeated 50 times), `twoHostBuildsCoexistWhenVmStopped`, `thirdHostBuildRefused`, `lightJobHoldsSlot2SoSecondHostBuildRefused`, `hostBuildRefusedWhileHeavyHeld`, `heavyRefusedWhileHostBuildHeld`, `killedHolderReleasesLock` (SIGKILL the holder, the next acquire succeeds), `nonBlockingNeverWaits`, `lockFilesLiveOutsideRepo`, `shellShimContainsNoLockLogic` (grep), `everyEntryPointUsesLauncher` (grep: no `podman run`, `podman machine start` or `gradlew`/`gradle` invocation in `tools/` or `pca_helper/` outside the launcher call).
**Mutation:** change the host-build acquisition from `LOCK_SH` to `LOCK_EX`; `twoHostBuildsCoexistWhenVmStopped` fails. Replace the heavy `LOCK_EX` by `LOCK_SH`; `simultaneousHeavyAndHostBuildExactlyOneWins` fails.

## 5. Shared-resource rules (8 GB Mac, binding for all of 3b, copied into part B/C)
1. **Before any VM-heavy job** (spike S3 or `verify`/`setup`): Opera closed (`pgrep -x Opera` empty) and `memory_pressure` free percentage >= 25 %; helper `doctor` checks both and refuses (`resources_busy`) otherwise, never kills anything.
2. **One lock protocol for every entry point (round 1, finding 6; master R12; implemented by L1 in `tools/canvas-helper/pca_lock.py`).** `heavy.lock` is taken **shared** by host Gradle builds and **exclusive** by VM-heavy jobs (`verify`, `setup`, S3a/S3b, H27a/b, H28 live); `host-slot-1.lock` and `host-slot-2.lock` limit host builds to 2; a VM-light job (gen, py_exec, S1, S2c, H13, H22) holds `light.lock` and `host-slot-2.lock`, so only one host build can run next to it; all acquisitions are non-blocking `fcntl.flock` calls in a fixed order, and the kernel releases them when the holder dies. Resulting ceilings: VM stopped = 2 host builds (`--no-daemon -Dorg.gradle.workers.max=2`); VM light job = 1 host build (`-Dorg.gradle.jvmargs=-Xmx2g`); VM heavy job = 0 host builds; at most 1 Gradle inside the VM. A host build when the VM is up and idle gets slot 1 only.
3. The shell wrapper `tools/with-build-slot.sh`, the Python helper (`pca_helper/` runner, `doctor`, `setup`), `gw.sh` if present, and every spike command all call the same launcher; a second, different mechanism (mkdir slots, separate flock files) is a defect (test `everyEntryPointUsesLauncher`).
4. `gen` and `verify` never run at the same time; **the 3b helper runs ONE leased job at a time (master plan R14), so no two VM jobs ever run together.**
5. The VM is started on demand (through the launcher) and stopped when the helper has been idle for 10 minutes (`podman machine stop`); Phase-0 spikes stop it at the end of each session.
6. Disk: `doctor` fails (`disk_low`) when host free < 15 GB or VM `/var` used > 17 GiB; `podman system prune` is run by the user, never automatically on volumes (`pca-gradle-ro` must survive).

### 6.1 Enforcing the output boundary (round 1, finding 1)
- **The enforcing boundary is a kernel limit, not a poller.** Each job gets a VM-local filesystem created by `container/vm/pca-jobfs.sh create <job> <bytes> <inodes> [noexec]`: a sparse image `/var/lib/pca/jobs/<job>.img` (`truncate -s`), `mkfs.ext4 -q -N <inodes> -m 0 -O ^has_journal`, mounted with `sudo mount -o loop,nosuid,nodev[,noexec]` at `/var/lib/pca/mnt/<job>`, `chown`ed for the container's mapped uid (through `podman unshare chown` or the `:U` volume option; S2c records which works). Only these paths are mounted rw into a container (`-v /var/lib/pca/mnt/<job>/out:/out`); a writer therefore hits `ENOSPC` at the byte limit and at the inode limit **immediately, between any two polls**, and cannot reach the Mac. The ordinary named volume is **not** used for limits (it has none). `tmpfs ...,size=,nr_inodes=` is the documented alternative for outputs under 64 MiB when memory accounting allows (the bytes then count against the container's memory limit); S2c records which mechanism each profile uses.
- **The `du` poller (2 s) is kept only as a backstop** (it kills by container name at 95 % of the limit and records the event); it is never cited as the boundary in tests or evidence.
- **Export after termination.** After the container is confirmed gone, `pca-jobfs.sh export <job> /stage/<job>/export` (trusted VM-side code, not generated code) copies with `cp -a --no-dereference` into the host stage tree, first checking that free bytes on `/stage` exceed the quota; the Mac collector (part-C H8) then validates the copy (no symlink, special file, hard link, depth/count/byte caps) before any content is read. `pca-jobfs.sh remove <job>` unmounts and deletes the image. Orphan images are swept by part-C H4 on helper start.
- **Live tests required:** N16 (fast writes), N18 (sparse files), N19 (inode exhaustion), N20 (bounded export) in S2c; the same cases against the real `py_exec` filesystem in H7b (live), the `gen` workspace in H22 and the verify scratch in H27a.

## 1. Goal (user direction, binding)
An MLflow/Dagster-like DAG canvas. The user defines new nodes (processes, prompts), connects them to existing components, bulk-tests N photos, freezes the winner, and the **router → intent → memory** stack goes live. The intent step classifies the activity in the image (`sitting_idle | workout | computer_work | driving | walking | other`) and routes each photo to an intent-specific prompt. Later the motion/context hub (wave B) feeds it, and the rest-vs-motion connectors are user-defined sources.

## 3. Headless JS tests (item 1)
The MVP JavaScript was never executed: only source scans ran.
- Ruling S3: the tests use **GraalJS** (`org.graalvm.polyglot:polyglot` + `js-community`, the newest 23.1.x, which runs on JDK 17 in interpreter mode), as a `testImplementation` in `:phone` only, in plain JUnit tests with no Robolectric and no WebView — it is the only JVM engine with full ES2020 and ES modules, and the bundle is modules. Rhino has no `import`/`export` and no `class`. QuickJS bindings need host native libraries. There is no Node on the machine — cost if wrong: about 40 MB of test-only jars in the Gradle cache. No APK change.
- **Structure:** logic lives in pure modules that never touch `document`, `window` or React: `graph.js` (pipeline model operations), `validate.js` (client port check), `keys.js` (keyboard decisions), `flowadapter.js` (pipeline ↔ React Flow, §4.2), `paramform.js` (param descriptors → inspector field model), `format.js` and `diffview.js`. The DOM modules are thin: `dom.js` (`h`/`btn` for the non-canvas views), `views.js`, `app.js`, and `floweditor.js`, the **only** file that touches React.
- **Harness** (`JsHarness`, Kotlin, test source set, built in Task 1): it loads ES modules straight from `phone/src/main/assets/canvas/` and the JS test files from `phone/src/test/js/`. Each test file exports `tests = { name: fn }`, and the harness runs them and reports the failing names. Its **fake DOM** (`fake-dom.js`) covers `dom.js` and the `views.js` smoke tests. React and React Flow are **not** run under GraalJS (no layout engine, no `ResizeObserver`); `floweditor.js` stays declarative and is covered by the browser checklist (Task 14).
- **Parse check:** every one of our `.js` assets is parsed as a module, so a syntax error anywhere, `views.js` and `app.js` included, fails the build. Vendored files (`vendor-*.js`) are excluded: they are UMD scripts, not modules, and are pinned by SHA-256 instead (§4.1).
- Alternatives considered for the harness and rejected: a headless browser (no Node or Chrome in the Gradle test path), Rhino and Nashorn (no ES modules), QuickJS/J2V8 (host native libraries), and `linkedom` (ISC, 594 KB `worker.js`) in place of the fake DOM (Task 1's fake DOM already exists, and linkedom would still not let React Flow lay out).

### 4.2 Modules
- **Kept as planned** (pure, GraalJS-tested): `graph.js` (`nextId`, `addNode`, `removeNode`, `connect`, `disconnect`, `setParam`, `setTitle`, `branchesOf`), `validate.js` (`portCheck`, `problemsByNode`) and `keys.js` (`move`, `reduce`), with the contracts and reason texts of the original plan Task 11.
- **New, pure: `flowadapter.js`** (no React import):
  - `toFlow(pipe, layout, problems, nodeTypes, opts) → {nodes, edges}`. Positions come from the `FlowLayouts` cells (`x = column × 220`, `y = layer × 120`). Nodes that are not in the layout yet (added while `/api/validate` is pending) go in a pending row below the last layer, in id order, with `data.pending = true`. Each node carries `data` = title, type label, input/output port types, problem texts and a domain colour key; `deletable = false` for `input.photos` and for everything when read-only; `connectable = false` when read-only. Each edge carries `ariaLabel` "<from> to <to> [when]", a `when` label, and a problem class.
  - `canConnect(conn, pipe, nodeTypes) → {ok, reason}`: wraps `validate.portCheck` and `graph.connect`'s refusals (cycle, duplicate, self), and refuses cross-domain edges (a no-op in slice 2, where every node is ASYNC; slice 3 relies on it). The reason text is the existing one, for example "Facts from frames accepts Photo or JSON, not Preview".
  - `applyChange(draft, change, nodeTypes) → {pipe, error?}`: maps `{kind: add|connect|remove|removeEdge|param|title}` onto `graph.js` operations. `add` uses a `<short>_<n>` id; `connect` carries `when` (the first unused branch when none was picked); `remove` drops the node's edges.
- **New, pure: `paramform.js`**: turns `/api/node-types` param descriptors (`{name, kind: int|bool|text|prompt|role|schema|labels, min?, max?}`) into a field model `{name, control, label, min?, max?, value, error?}` and coerces and range-checks input (`coerce(field, raw) → {value, error?}`). Slice 3 extends it to its JSON Schema subset (§4.6).
- **New, thin: `floweditor.js`**, the only file that touches React (`const html = htm.bind(React.createElement)`; components from `globalThis.ReactFlow`):
  - a controlled `ReactFlow` with `nodesDraggable=false`, `nodesFocusable`, `edgesFocusable`, `nodeTypes={{card: NodeCard}}`, `deleteKeyCode={['Delete', 'Backspace']}`, `fitView`, pinch and pan on;
  - `NodeCard`: typed `Handle`s (target on top, source on the bottom), a problem badge, `aria-describedby` pointing at a hidden list of its problem texts;
  - `isValidConnection = c => canConnect(c, …).ok`; `onConnectEnd` shows the refusal reason in a `role="status"` line; `onConnect` from a branching source opens a small `when` popover (first unused branch pre-selected);
  - `onBeforeDelete`/`onNodesDelete`/`onEdgesDelete` → `applyChange(remove…)`; `onNodesChange` is used for selection only;
  - the palette and the inspector (below), the problem list, and the 250 ms debounced `POST /api/validate` whose `layout` and `problems` feed `toFlow` again.

### 4.3 Behaviour (unchanged from the original §4, mapped onto React Flow)
- **Palette:** one button per node type where `palette` is true, grouped by `category` (Task 9 serves a category per type; slice 3's registry replaces it). Enter on a button, or dragging it onto the pane (HTML5 drag plus `screenToFlowPosition`; on touch, a tap then a tap on the pane), adds the node after the selected node. Ids are `<short>_<n>`.
- **Connect:** drag from a node's source handle to a target. While dragging, `isValidConnection` marks the allowed and refused targets (React Flow's `valid`/`invalid` handle classes). A refused drop shows the reason inline.
- **Remove:** select a node or an edge (both focusable), then press Delete or use the inspector's Remove button. Removing a node removes its edges. `input.photos` can't be removed.
- **Layout:** Ruling S4 is unchanged: no hand-placed positions, `FlowLayouts` is the only layout, nothing about position is stored, and `nodesDraggable=false` enforces it.
- **Validation inline:** as before (`Problem(text, nodeId?, edge?)`, red outline plus badge plus `aria-describedby`; dashed red edge; the list under the canvas focuses its node). The client checks port types only; the server is the authority.
- **Keyboard:** Tab moves into the canvas (React Flow's own node and edge focus). One `onKeyDown` on the wrapper delegates to `keys.js`: the arrows move focus by layer and column (focus the node's element; React Flow auto-pans to it), `c` starts connect mode (arrows pick a target, Enter connects through `applyChange`, Esc cancels), `a` focuses the palette. Delete removes. Because nodes are not draggable, React Flow's arrow-to-move is inert; if it still fights `keys.js`, set `disableKeyboardA11y` and keep `nodesFocusable` (evaluation §4 risk 2). Every action has a button equivalent. Focus is always visible.
- **Inspector:** rendered from `paramform.js` for the selected node, plus Title and Remove. Prompt templates and schemas stay `<textarea>`s (native, accessible; no code editor library in slice 2).
- **One draft model:** the inspector, the JSON panel, Save and Freeze all read the editor's single in-memory draft, as before. Freeze while dirty saves first. Leaving with unsaved changes asks for confirmation.
- **Pointer, touch and pen** come from React Flow. On a 360 px phone the pane pans and pinch-zooms inside its own container. Built-in pipelines are read-only (`deletable`/`connectable` false, the palette hidden, "Duplicate to edit").

### 4.5 Risks (evaluation §4) and their checks
1. GraalJS cannot run React: logic stays in the pure modules; `floweditor.js` is covered by the browser checklist.

4. UMD/shim brittleness: exact pins, SHA-256 lock, deliberate upgrades.
5. Phone performance: tens of nodes; the first render on the phone is timed once in the checklist.

## 5. Interpreter and the intent stack (item 2)
**Interpretable shape** (`InterpretableShape.problems(p)`, in `:services:ai`):
- the pipeline is valid;
- before the extraction tier, it contains only `input.photos`, `ai.prompt` and `route.switch` nodes;
- every path from `input.photos` reaches exactly one `ai.vision_extract`;
- after an extract node there are only `gate.local_critic`, `ai.critic` (whose prompt must be Live) and `memory.write`;
- there are at most 3 `ai.prompt` nodes;
- before extraction, only a `route.switch` may have more than one out-edge (one per distinct `when`), and every switch branch, `other` included, is wired (S28).

The default `intent-draft` pipeline passes, once its `other` branch is wired (S28).

- Ruling S5: the live save tail is always the live one. After the interpreter produces the facts and captions, today's code runs unchanged: the claim CAS, `saveExtraction`, the local trust check, the model critic with the active CRITIC prompt, embeddings and nudges. Trust and critic nodes in the pipeline only shape experiment previews, and the publish dialog says so — the save path keeps its invariants (claims, Forget fence, wipe generation) — cost if wrong: an experiment preview with no trust node can look more permissive than what live saves.
- **Seam:** in `KeyframeHandle.extract`, the line `ExtractSave.extract(ai.runner, photos, callClass)` becomes `LiveExtract.batch(photos, callClass)`. When no interpreter publish is active, it calls exactly that same line. When one is active in Live mode, `PipelineInterpreter` runs the pipeline's pre-save nodes with the **same canvas executors** (`RunContext.callClass` = the live call class; "what you test is what ships"). It merges the per-item extractions into one `ExtractedBatch` (facts de-duplicated by text, type and source-frame set) and returns it. The rest of `extract` is untouched. **Round 3:** the batch comes back with its buffered effects (trace rows and labels), which are committed by `LiveExtract.commit` only after `saveExtraction` returns `Saved`, fenced by the generation captured before the photos were loaded (S24, S29). With no interpreter publish, the effects are empty and the commit touches nothing. The interpreter runs under a 4-minute deadline (S30).
- **Fallback:** Ruling S6: when the interpreter fails for a batch for any reason other than a transient network failure that S23 rethrows (it propagates exactly as live does today), the whole batch is extracted by the live `ExtractSave.extract`, and one `_batch` ERROR trace row per photo is written. When 10 of the last 30 interpreted photos of this publish fell back, the publish is **auto rolled back** (`rollbackReason = "auto: 10 of 30 fell back"`) — memories are never lost to an experiment, and a broken prompt cannot stay live for long — cost if wrong: a failing batch costs one extra call.
- **Cost:** Ruling S7: the intent call (and any other `ai.prompt` node) runs once per photo at the **live call class**, charged to the live `CallBudget`. A batch of 3 photos becomes about 3 intent calls plus 1–3 extract calls instead of 1. The publish dialog shows "about N–M× the model calls of Live extraction", a range computed from the shape, the extractors' batch sizes and the branch fan-out (S33) — it's the honest price of the stack — cost if wrong: the live backlog grows on slow budgets. Shadow mode (below) measures it first.
- **Modes:** Ruling S8: an interpreter publish has a mode. In **Shadow**, live extraction stays as it is, and on 1 in 4 live batches (after the live save) the interpreter runs as `CallClass.EXPERIMENT`, saving trace rows only. Shadow pauses while Developer mode is off. In **Live**, the interpreter replaces the extraction step. Live stays live when Developer mode is off, just as published prompts do, and Diagnostics always shows "Live pipeline: <name> v<N> (canvas)". Going from Shadow to Live is a new publish of the same version — the same staging the MVP spec planned for slice 3, minus canary — cost if wrong: there is no canary percentage. Live is all batches at once, protected by S6.
- **Intent label:** Ruling S9: the canvas records the label in its own photo-derived table `canvas_live_trace` (the per-node outputs of every interpreted photo). The live label is also handed to `FrameIntentSink.record(frameId, label, confidence, atMs)`. The default is a no-op. **Wave B owns the `frame_meta` intent column and its writer**, and binds the sink when it lands. The canvas only **reads** that column, after wave B is merged (one swap in `FrameIntentReader`, listed in the device checklist) — this follows the user's ownership split, and a canvas branch cannot compile against a column that doesn't exist yet — cost if wrong: until wave B, the label lives only in canvas tables (it is wiped and forgotten like other canvas data).
- **The label as context:** as in the MVP, the switch passes the intent JSON downstream, and the extract executors put it in `{{context_sources}}` as the `upstream` data block.
- **The deterministic signals and the fusion node** (car Bluetooth, GPS, Activity Recognition, watch, user-defined rest-vs-motion sources) stay in wave B and slice 3. `RouteInput` and the node registry stay open for an `input.signals` node.

## 6. Freeze, publish, roll back, diff (item 3)
- **One publish stack:** Ruling S10: interpreter publishes are rows in the existing `canvas_publish` table, with new columns `kind` (`prompts` | `interpreter`), `mode` (`SHADOW` | `LIVE` | null) and `rollbackReason`. "Roll back" always undoes the newest active row of either kind. The active interpreter is the newest non-rolled-back interpreter row — one Roll back button with stack semantics the user already knows — cost if wrong: you can't roll back an older interpreter publish without first undoing a newer prompt publish.
- **Interpreter publish gates:**
  1. `InterpretableShape` has no problems;
  2. `TestBed.compatibility(VISION_EXTRACT, draft)` is clean for every draft extract prompt;
  3. every `ai.prompt` schema parses;
  4. there is a DONE run of this exact hash with an OK item at every AI node.

  The reason texts are fixed. Publishing writes no prompts: the interpreter reads the frozen version's JSON, so the per-intent prompts live in the version.
- **Live-shaped** pipelines keep the MVP prompt publish (`kind = prompts`). Its saves now go through compare-and-set (§9).
- **Diff view:** `PipelineDiff.of(a, b)` lists the nodes added, removed or changed (with the params that changed), the edges added or removed, and a `LineDiff` per prompt template or schema. It compares any two versions, or a version against the draft. The UI route is `#/p/<id>/diff?a=<v>&b=<v|draft>`.

## 7. A/B runs, usage and estimate (items 2 and 8)
- **A/B:** Ruling S11: an A/B run is two ordinary runs (A, then B) over the same photos, linked by `canvas_run.abGroup`, behind one estimate (the sum of both, still at most 200 nominal calls and 50 photos) and one confirm. B starts when A ends DONE. Cancel cancels the group. Both run ids are reserved up front, and the group owns cancellation and runner exclusion (S31). When B ends, the compare view opens — it reuses the runner, the storage and the compare view unchanged — cost if wrong: B runs a few minutes after A, so a provider-side change in between can skew it.
- **Intent summary:** for every `route.switch`, the run and compare views show the count per branch. For an A/B pair they also show the agreement rate (the share of photos whose branch is the same in A and B), and the score sums per node per run.
- **Usage:** `ExtractedBatch` gains an additive `attempts: List<CallUsage>` (one entry per provider attempt, retries and the single-photo fallback included; empty by default), so extract items finally record tokens, counted once per call, not once per photo (S32). Each run shows "calls X (estimated Y) · tokens in/out · median latency".
- **Estimate:** Ruling S12: next to calls, the estimate shows tokens: the per-node-type mean of prompt and completion tokens over that type's last 200 OK items. There is no money figure — the app has no pricing data — cost if wrong: the user converts tokens to cost by hand.
- **Diagnostics:** the calls line names `EXPERIMENT` ("EXPERIMENT N" per hour, from `BudgetStats.callsLastHour`) and stops folding it into OTHER. When an interpreter publish is active, the line "Live pipeline: …" with its mode and fallback count.

## 8. Ask debug and replay (item 4)
- **Views:** `#/asks` lists the newest 50 asks (time, question, a short answer, rating). `#/ask/<id>` shows:
  - the question, the stored answer and the cited sources;
  - **"Retrieved as of then"**: the hits with lexical, semantic, fused and final score, the mode used, and whether each was cited, plus the memory text and frame thumbnail;
  - the **composed prompt** (SYSTEM + ANSWER with the variables filled in), read-only;
  - an ANSWER template editor prefilled from the active prompt, with Check, then **Replay** (one model call, confirmed), which shows the new answer, its sources, its latency and its tokens.
- Ruling S13: retrieval for the view is **re-run** with `nowMs = ask.ts`, dropping memories created after the ask. The original retrieved set and its scores were never stored, and the view says "re-retrieved; may differ if settings or embeddings changed". Recording live retrieval traces would be a live-path change for a debug view. A replay is not persisted, runs as `CallClass.EXPERIMENT`, never saves an ask or a proposal, and is refused for redacted asks. The time bound is applied before the retriever's limits (S34), and the replay result is fenced like a live answer (S35) — cost if wrong: the scores shown can differ from what the ask really saw, after a settings change or a re-index.
- Ruling S14: this is a view, not `input.asks` / `ai.answer` nodes. The runner is built around photo items, and the user asked for "pick an ask … replay" — cost if wrong: no bulk replay of N asks until slice 3.

## 9. Compare-and-set prompt save (item 5)
- `PromptDao.casSave(id, expectTemplate, expectSchema, template, schema, note, testedOk, now, keepVersions): Int?` runs in one transaction. It reads the active version, compares its text **exactly** (template and schema), and then appends or overwrites as `save` does. It returns null on a mismatch.
- `PromptRepository.saveAllIfUnchanged(edits: List<CasEdit>): CasResult` runs every key in **one** transaction, so if any key mismatches, nothing is written.
- `CanvasPublisher.publish` (prompts) and `rollback` use it. This closes the parked window (Task 7 b) and the half-done multi-key rollback.
- **Round 3:** the prompt writes and the `canvas_publish` row (insert, or the rollback mark) commit in **one** Room transaction (S27).
- Ruling S15: the comparison is on exact text inside the transaction, not on version number — with versioning off, the version number doesn't change when the text does — cost if wrong: nothing.

## 10. Secure LAN (item 6)
- Ruling S16: when LAN is on, the server speaks **HTTPS only**, with a self-signed EC P-256 certificate generated in the AndroidKeyStore (alias `pc_canvas_tls`, valid for 825 days, rotatable). Loopback with LAN off stays HTTP, because loopback cannot be sniffed. Plain-HTTP LAN is removed: if the keystore TLS fails on the phone, the LAN switch is disabled with "Secure LAN isn't available on this phone". The app shows the certificate's SHA-256 fingerprint (8 groups of 4 hex). The laptop browser warns once, and the user compares the fingerprint in the browser's certificate details. The app's WebView **pins** it: `onReceivedSslError` proceeds only when the presented certificate's SHA-256 equals ours — TLS defeats passive sniffing even when the fingerprint is never checked, and active interception when it is — cost if wrong: a browser warning on the first visit from each laptop. If AndroidKeyStore keys can't serve TLS on this phone, LAN is unavailable until a software-key fallback is added.
- The Origin rule becomes `<scheme>://<Host>`. The WebView URL is `https://127.0.0.1:<port>/` while LAN is on.
- **Round 3:** the key authorises the TLS signing digests (S36). The WebView reloads, and clears its retained SSL decisions, whenever the scheme, port, certificate or token changes (S37).
- **Pairing hardening** (final-review M4): Ruling S17: after a lockout, no new code is minted automatically: the user taps "New code". Lockouts escalate (30 s, 2 min, 10 min) — this removes the endless 5-guesses-per-30-s window — cost if wrong: one extra tap after a typo streak.

## 13. Round 3 rulings (Codex plan review)
Finding numbers are those of the §0 table. The actual failure kinds (checked on `canvas/integration`, `services/ai/.../ModelErrors.kt`) are `NOT_SET, AUTH, REJECTED, INVALID_OUTPUT, TRANSIENT`. `CallBudget.withPermit` **suspends** while waiting for a permit; it never throws a budget exception.

### 13.1 Live seam and interpreter
- Ruling S23 (#1, failure classes): the interpreter rethrows only failures the fallback would hit too, read over the cause chain the way `ExtractOutcome.classify` reads it: an `IOException` (an `InterruptedIOException` included) in the chain, or a `ModelCallException` with `kind == TRANSIENT && retryable`. Everything else is `Failed`, and the batch takes the S6 fallback. That includes `INVALID_OUTPUT` and `NOT_SET` even when `retryable = true` (`AnswerService` and `ModelRouter` throw both that way), plus `AUTH`, `REJECTED` and any other throwable. The fallback's own exception then propagates exactly as live does today, so an unbound VISION_EXTRACT role still pauses the loop as "provider NOT_SET". `CancellationException` is always rethrown, but S30's deadline is not treated as a cancellation. NETWORK, TIMEOUT, RATE_LIMIT and BUDGET kinds don't exist and are not used — a misconfigured intent role must never leave photos unprocessed or slip past auto-rollback — cost if wrong: an offline blip during an intent call costs one live retry instead of a fallback call.
- Ruling S24 (#2, fences on every derived write): every canvas write derived from photos is fenced at commit. Inside the write transaction it rechecks two things: the wipe generation captured **before** the photos were loaded (the same `generation` that `KeyframeHandle.extract` already captures), and the frames' tombstones. A mismatch drops the whole write. The fence covers `canvas_live_trace` (Live and Shadow), the experiment runner's `canvas_run_item`/`canvas_score` writes, and the intent sink. Live effects (trace rows and labels) are buffered per batch in `LiveEffects`. `LiveExtract.commit` commits them only after `saveExtraction` returns `Saved`, and only for the saved frames. On a fallback the labels are discarded, but the `_batch` ERROR rows are still committed (fenced) after the fallback's save, because S6 counts them. This is slice 3 S35's EffectBuffer in its smallest form — deleted data must not come back — cost if wrong: a label reaches the sink a few seconds later, after the save.
- Ruling S28 (#6, exclusive and complete routing): before extraction, only `route.switch` may have more than one out-edge, each on a distinct `when`. Every other pre-save node has exactly one out-edge. Every switch branch, `other` included, must be wired: the old rule that ignored an unwired `other` path is dropped. The new fixed texts are `"node <id>: only a switch can send photos down two paths"` and `"node <id>: branch <b> isn't connected"`. Two more fixed texts (ratified in fix round 1): `"node <id>: branch <b> goes to more than one node"` (a switch branch wired to two nodes) and `"node <id>: extraction can only continue to one node"` (an extractor with 2+ out-edges; the "only a switch" text is for input and prompt nodes). Task 9 serves them, and the JS validator list for Task 11b/11e must know all four. At run time, an item that reaches 0 or 2+ extractors is `Failed("routing")`. The `intent-draft` seed wires `other` to a generic extract — parallel extractors duplicate extraction, and an unwired `other` would force a fallback for every unlabelled photo — cost if wrong: the user wires `other` once per pipeline.
- Ruling S29 (#7, telemetry boundary): extraction and telemetry are separate. `LiveExtract.batch` only produces the batch (the interpreter's, or the fallback's) plus its effects. A failure to load or decode the version is `Failed("internal")`, which falls back. Trace commits, the sink, fallback counting and the auto-rollback check all run in `LiveExtract.commit`, after the save, each step in its own `runCatching` that rethrows cancellation. A failure there is logged by class name and never changes the returned batch or the save. The auto-rollback check runs inside `commit` before it returns, not after a `return`. Every call returns exactly one batch — a debug table must never cost a memory — cost if wrong: auto-rollback can lag one batch while the DAO is failing.
- Ruling S30 (#8, deadline): `LiveExtract.INTERPRETER_DEADLINE_MS = 240_000`, applied with `withTimeoutOrNull` around `interpreter.run`. It includes budget waits and holds for Live and Shadow alike. On expiry the batch is `Failed("deadline")` and falls back. That leaves at least 6 of the `ExtractWakeLock`'s 10 minutes (and of the 15-minute claim timeout) for one live extraction and the save. There is no claim renewal and no wake-lock change — 3 prompt nodes over 3 photos are 9 sequential calls before extraction — cost if wrong: on a slow provider, intent batches fall back, and S6 then auto-rolls the publish back.
- Ruling S42 (#20, provenance): `NodeResult` carries the executor's `ExtractedBatch`, not only `CanvasValue.Extraction`, so the interpreter can merge `output.provenance` (true only when every extract chunk had it) — the save path reads it — cost if wrong: none.

### 13.2 Deletion, storage, publish journal
- Ruling S25 (#3, deletion follows the call): every `canvas_run_item` and `canvas_live_trace` row carries the `batchId` of the provider call that produced it. Run items already have the column; the trace table gets it in Task 4. Forgetting frame A deletes A's rows, **every row that shares a `batchId` with any of them**, and their scores. Prompt-node and switch rows are per photo, so other photos' rows survive. Each cluster-summary call (Task 13) has one `batchId`, so forgetting one member clears that call's rows for the whole cluster. Frame retention deletes use the same cascade. This is leaner than a per-output dependency table, and it is slice 3 S38's provenance rule at batch granularity — `VisionExtractExecutor` copies a fact citing A+B into both rows — cost if wrong: forgetting one photo also clears the canvas debug rows of up to 2 batch-mates (never their memories).
- Ruling S26 (#4, one canonical lineage): the Room lineage is v3 (canvas MVP) → v4 (wave 2) → v5 (wave B `MIGRATION_4_5`) → v6 (slice 2). A provisional number exists only inside a branch's unit tests: an APK whose schema isn't on the canonical line is never installed, and Task 14 installs only integration-line builds. Slice 2 Task 4 lands on the integration line only after wave B's `MIGRATION_4_5` and `5.json` are there. If wave B's other tasks are later, its migration commit (Task 9's additive `frame_meta` columns, nothing else) lands first, on its own. This corrects the handoff's planned merge order, which lists wave B after slice 2. Migration tests start from **each canonical exported schema** (`3.json`, `4.json`, `5.json` → `6.json`), not only from v1 — renumbering can't repair a phone that already opened a provisional schema — cost if wrong: slice 2's Task 4 waits for one small wave B commit. See §15 item 19.
- Ruling S27 (#5, one transaction for prompts and the journal): `a208852` already fingerprints what the CAS wrote (the accepted drafts, not a re-read) and uses one read per key for the rollback expectation and the legacy-fingerprint check. What remains is the transaction: the prompt CAS and the `canvas_publish` insert, or the rollback's `markRolledBack`, run in **one** Room transaction (`db.withTransaction { casSaveAll(…); insertPublish(…) }`; both DAOs live in `ContextDatabase`). The legacy-fingerprint check runs inside it. A failure between the writes rolls both back — a crash must not leave prompts changed with no rollback record — cost if wrong: none. This is new plan Task 2b.
- Ruling S44 (#22, retention without an interpreter): `CanvasMaintenance.pruneTraces()` (7 days or 5,000 rows, at most hourly) runs on canvas server start, on every `/api/live` and `/api/publish*` read, and once from `CanvasGraph` init in the background. The live path no longer prunes inline, which also satisfies S29 — traces must expire after a rollback too — cost if wrong: none.

### 13.3 A/B, usage, estimate
- Ruling S31 (#9, A/B groups): `startAb` inserts both run rows up front (A RUNNING, B QUEUED, the same `abGroup`) and returns `AbStarted(group, runA, runB)`. The group owns cancellation: `cancelGroup`, and cancelling either run, cancels both, including in the window between A ending and B starting. The group also owns runner exclusion: no other run starts while the group has a QUEUED or RUNNING row. On process start, the existing run recovery marks every QUEUED or RUNNING row of a group CANCELLED. The API returns `{group, runA, runB}` — it closes the A→B gap — cost if wrong: none.
- Ruling S32 (#10, usage per call): `ExtractedBatch` gains `attempts: List<CallUsage(promptTokens?, completionTokens?, model?, latencyMs)>`, one entry per provider attempt, covering rejected-output retries and single-photo fallback calls. It replaces the three planned scalar fields. Executors still write per-item `CallMeta` with the call's `batchId`, but only the first item of each `batchId` owns the usage: it gets the summed tokens and `calls = attempts.size`, and the other items get null. Run usage sums the owner rows, and `tokenMeans` becomes a per-call mean (Σ tokens / Σ calls) — a three-photo batch was counted three times, and retries not at all — cost if wrong: one nullable column (`canvas_run_item.calls`).
- Ruling S33 (#11, call range): `callFactor` becomes `callRange(p) → (min, max)` for a batch of 3 photos, relative to Live's 1 call. A photo's prompt calls are the prompt nodes on its path. Extract calls are, for each extractor, ceil(photos routed there / that extractor's batch size). The minimum puts all 3 photos on the cheapest path; the maximum spreads them over the most expensive distinct paths (one path per photo, by S28). The dialog reads "about 4–6× the model calls of Live extraction" — a single number hid the batch-size and label-mix effects — cost if wrong: none.

### 13.4 Ask debug
- Ruling S34 (#12, time bound before limits): `notAfterMs` is passed into `MemoryRetriever` (an additive parameter; null keeps today's behaviour) and applied **before** every limit: the lexical candidate query, the semantic candidate set, the top-k and the newest-30 fallback — newer memories would otherwise crowd out every historical hit — cost if wrong: none.
- Ruling S35 (#13, replay fence): before the call, replay captures the wipe generation and the retrieved memory ids. After the reply it rechecks, as `AnswerService.answerOrThrow` does, that the ask isn't redacted, the generation hasn't changed and every retrieved memory is still live. If any check fails, the result is `Failed("forgotten")` and carries no text — forgotten text must not reach the screen — cost if wrong: none.

### 13.5 Secure LAN
- Ruling S36 (#14, keystore digests; narrowed): the `KeyGenParameterSpec` authorises `DIGEST_NONE, DIGEST_SHA256, DIGEST_SHA384, DIGEST_SHA512` for `PURPOSE_SIGN`. A real AndroidKeyStore handshake test (`KeystoreTlsDeviceTest`, `:phone` androidTest, TLS 1.2 and 1.3 against a loopback server) is compile-verified in Task 10 and run on the phone in Task 14, after the install. The **test fixture** gets loopback SANs (`keytool … -ext SAN=IP:127.0.0.1,DNS:localhost`). **Narrowed:** the keystore certificate itself carries no SAN, because `KeyGenParameterSpec` can't set one and the plan allows no new dependency. Browsers warn on first visit anyway, and the WebView pins by fingerprint, not by name. The device test uses a hostname verifier that accepts only the pinned certificate. If the handshake fails on the phone, S16's "Secure LAN isn't available" path applies — TLS keys commonly need `DIGEST_NONE` — cost if wrong: none beyond S16.
- Ruling S37 (#15, WebView lifecycle): `CanvasWebRoute` is keyed on `(scheme, port, fingerprint, token)`. When any of them changes (the LAN toggle, a port fallback, New certificate, a re-pair), it calls `WebView.clearSslPreferences()` and loads the new URL. It also clears them on first creation. The pinning test drives the real `onReceivedSslError` with Robolectric `SslError` objects built from the fixture certificate and from a second certificate (proceed vs cancel). `SslDecision` stays as the pure helper — WebView can keep an earlier SSL decision — cost if wrong: none.

### 13.6 Editor and web tests
- Ruling S38 (#16, draft revisions): a pure `draftstate.js` (Task 11d) holds `rev`. Every `applyChange` bumps it, every `/api/validate` call carries the rev it was sent at, and a reply is applied only when its rev equals the current one: older replies are dropped. Save-and-freeze sets the editor `readOnly` until it finishes, and Freeze sends the `draftRev` the save returned. The server refuses a stale freeze with 409 `conflict` "The draft changed. Save again." (an additive optional `draftRev` on `POST /api/pipelines/{id}/freeze`). React Flow stays a pure view of `toFlow` — debouncing alone lets an old reply overwrite a newer layout — cost if wrong: none.
- Ruling S39 (#17, the real boot under GraalJS): `app-routes.test.js` imports the real `app.js` with the fake DOM, a fake `fetch`, and stub `React`/`ReactDOM`/`ReactFlow`/`htm` globals. It navigates every route (`#/`, `#/p/<id>`, `#/p/<id>/diff`, `#/live`, `#/run/new`, `#/run/<id>`, `#/compare`, `#/asks`, `#/ask/<id>`) and asserts that each one renders without throwing. For that, `floweditor.js` reads `globalThis.React`/`ReactFlow` inside `mountEditor`, never at import time. The real React Flow still runs only in the browser checklist — a broken import or route would otherwise pass every test — cost if wrong: about 0.5 h.

### 13.7 Scene nodes, install safety, history
- Ruling S40 (#18, gated scene nodes): node types gain one `chunking` field (`PER_ITEM` (default) | `WHOLE_NODE` | `BY_CLUSTER`) that `CanvasRunner` reads. `scene.group` is `WHOLE_NODE`. `ai.cluster_summary` is `BY_CLUSTER`, packing ≤ 3 clusters and ≤ 6 photos per call, and calls through `ClusterContract.call`, its retries included. Nominal and max calls come from that packing and the contract's retry count. The tests go through `CanvasRunner`, not the executor alone — `chunkSize = 1` prevented the grouping — cost if wrong: none (the task stays gated).
- Ruling S41 (#19, install safety; leaner): Memory Export is not a backup. Task 14 step 0 uses the handoff's existing full phone backup (the tar, counts only, never opened) and only `adb install -r`, **never** an uninstall, because uninstalling deletes the AndroidKeyStore key that opens the SQLCipher database. Migrations are validated on fixtures, never on production data. `SqlCipherMigrationDeviceTest` stays in `:services:memory` androidTest (its own test package, so neither the app's `Application` nor the production graph starts). It builds a fixture database at each canonical version (3, 4, 5) with its own key, migrates each to 6, and runs before the app APK is installed. This is leaner than copying production, which the sandbox and keystore make impractical — cost if wrong: a migration bug that only real data triggers is caught by the backup, not the test.
- Ruling S43 (#21, history): `GET /api/publish/history?limit=<≤ 50>` returns every row, newest first, with `kind`, `mode`, `pipelineId`, `version`, `publishedAt`, `rolledBackAt` and `rollbackReason`. The end-to-end test expects Shadow to be active after the first rollback and nothing after the second. Task 14 reads the auto-rollback reason from this route. Slice 3's group-aware history extends the same route — the active-stack route can't show rollbacks — cost if wrong: none.

Reviewed **3f1fd1ed**. Two security findings:

- **P1 — Debuggable checks fail open.** [.github/workflows/release.yml:143](/Users/debasishkanhar/Desktop/rokid/proactive-context-agent/.github/workflows/release.yml:143) treats an `aapt2` failure as “not debuggable”; the subsequent `echo "$(…)"` also hides failure. Both this check and [verify-release.sh:27](/Users/debasishkanhar/Desktop/rokid/proactive-context-agent/release/verify-release.sh:27) use `producer | grep -q` with `pipefail`: early grep exit can SIGPIPE the producer, turning a detected debug marker into a false condition. Reproduced both failure paths with shell fixtures. Capture badging with a checked assignment, validate its structure, then match without an early-closing pipe. Also sign with `--debuggable-apk-permitted false`.

- **P1 — Signing secrets lack a protected release boundary.** [release.yml:9](/Users/debasishkanhar/Desktop/rokid/proactive-context-agent/.github/workflows/release.yml:9) accepts any `v*` tag, including a collaborator’s tag pointing at unreviewed code; dispatch can likewise select a branch. That code executes before key decoding and can persist a background reader to steal the later signing material. Repository secrets provide no separation from write collaborators. Use restricted environment secrets with required reviewers and release-ref rules; repository protection settings were unavailable for verification. [GitHub documents this trust boundary](https://docs.github.com/en/actions/reference/security/secure-use).

Other findings:

- **P2 — Single-signer signing needs explicit scheme flags.** New-key-only signing with a debug→release lineage is valid for **v3**, with the new signer at the lineage tail. However, the command at [release.yml:117](/Users/debasishkanhar/Desktop/rokid/proactive-context-agent/.github/workflows/release.yml:117) leaves v1/v2 enabled by default; those require the **oldest signer’s private key**, so the command as written fails. Since all project minSdks are ≥28, explicitly disable v1/v2 and rehearse that exact form. A valid v3 APK with `--rotation-min-sdk-version 28` and installed-data capability can update the debug-signed installation on API 28+, preserving its data. Pre-28 Android cannot use lineage; compatible v1/v2 updates require the old key. [apksigner requirements](https://android.googlesource.com/platform/tools/apksig/+/master/src/apksigner/java/com/android/apksigner/help_sign.txt), [Android rotation support](https://source.android.com/docs/security/features/apksigning/v3).
- **P2 — Mutable supply chain:** checkout, setup-java and setup-gradle use `@v4`; runner/JDK/tool provisioning also floats. Pin action SHAs and constrain tool provenance. `cache-read-only` prevents this job writing caches, but does not establish restored-cache trust. [GitHub guidance](https://docs.github.com/en/actions/reference/security/secure-use).
- **P2 — Previous-version selection is bypassable:** `grep -vx "$TAG"` interprets regex; dispatch tag `v.*` removes every previous tag and skips comparison, reproduced locally. Use `grep -Fvx --`, validate tags, and select the intended predecessor. Missing history deliberately skips; missing source files and nonnumeric comparisons fail closed.

Placeholder/empty pins fail, and digest comparison checks exactly one **current signer**, not lineage ancestors. The standalone verifier fails on missing tools. The release command explicitly uses `--draft`, which leaves it unpublished. [CLI semantics](https://cli.github.com/manual/gh_release_create).

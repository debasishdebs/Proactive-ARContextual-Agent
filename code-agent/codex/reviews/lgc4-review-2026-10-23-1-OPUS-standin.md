## Findings

1. **Important (fence ordering: data written for a forgotten epoch after a restart).** TraceRecorder.kt:207-211 + :249-262 with :147. A new epoch (Delete all, counter N -> N+1, or a re-pairing) is adopted in memory only; `trace_epoch` keeps the OLD epoch on disk until the wipe AND `writeEpoch` succeed, and `wipeFailed` is volatile. Failure scenario (deterministic, no crash timing needed): diag ENABLED with epoch (inst-1, 0); phone sends Delete all (inst-1, 1); one file under `imu/traces/` cannot be deleted, so `wipe()` returns false and `wipeFailed=true`; the glasses reboot (or the process is killed while the wipe task is queued/running) and the phone is not reachable. On restart `readEpoch()` returns (inst-1, 0), `epochDurable = true` (:147), `wipeFailed=false`, `diag_state` = `1`, so `diagEnabled()` is true and `wantsStart` is true: new traces are recorded and tagged with the deleted epoch (inst-1, 0), next to the survivors of the failed wipe, until a control reaches the glasses. Before LGC4 the same restart recorded nothing (collect defaults to false), so LGC4 introduces this. Exact edit: make the old epoch non-durable on disk BEFORE the fence runs; in `enqueueWipeLocked`'s task (TraceRecorder.kt:252-254), first call a new `storage.clearEpoch()` (TraceStorage.kt, next to `writeEpoch` at :140: `fun clearEpoch(): Boolean { epochFile.delete(); return !epochFile.exists() }`) and treat a false result like a failed wipe (`ok = false`); only then `storage.wipe()` and `writeEpoch`. After a restart in any intermediate state `installId` is "" so the flag reads `armed_no_epoch`, nothing records, and the next control adopts and re-wipes. Add RED test in DiagBootstrapTest: `aFailedFenceThenOfflineRestartDoesNotRecordUnderTheForgottenEpoch` (boot; control(inst-1,0); onSettings(true); drain; mkdirs `imu/traces/keep`; failDelete=true; control(inst-1,1); drain; `boot()` again; assert `!wantsStart` and state `ARMED_NO_EPOCH`); it fails on 108b3122. The residual window between the in-memory adoption and the writer reaching the task (crash while recovery/finishJob are ahead in the queue) stays and is owned by LGC8-min (persist the received cleanup before acting, replay before recovery); state that dependency in the commit/plan so `lg/int-min` is not merged without LGC8-min.

2. **Minor.** TraceStorage.kt:140-145 `writeEpoch` is not fsynced and ignores the result of the second `part.renameTo(epochFile)`; `enqueueWipeLocked` then sets `saved = true` / `epochDurable = true` (TraceRecorder.kt:256-258) although nothing may be on disk. Safe direction (restart reads no epoch -> armed), but `epochSaved` claims durability it does not have, unlike `DiagStateFile.atomicWrite`. Edit: reuse `DiagStateFile.atomicWrite`-style temp+`fd.sync()`+checked rename and throw on failure so `saved` stays false.

3. **Minor.** HudController.kt:159 re-invokes `onPhoneSettings` from a `pc_state` Paused frame with `_settings.value` (initialised from `HudSettingsCache`, HudController.kt:62), so after LGC4 a state frame also drives `diagRecord.onSettings` (GlassesRuntime.kt:255) from the cached copy, a second source besides `diag_state`. The cache is written with `apply()` (HudSettingsCache.kt:40), so after a kill it can diverge from `diag_state`. Today the phone pushes settings before any state frame at session-ready (Hub.kt:360), so the stale value is overwritten at once; no live failure found. Edit: drive `diagRecord.onSettings` only from the real `pc_settings` path (e.g. a dedicated `onPhoneSettingsPush` callback fired at HudController.kt:174), not from the pause re-application.

4. **Minor.** DiagRecord.kt:98-104 reports `UNPROVISIONED` ("never contacted by a phone") whenever `requested=false` and the epoch is not durable, which includes a provisioned glasses during a fence or after a failed epoch write. Misleading on the LGC6-min status line; harmless to LGC4P (which retries only on `armed_no_epoch`). Edit: document it as "no durable epoch and not requested", or distinguish `installId.isNotEmpty()`.

5. **Minor.** DiagRecord.kt:113-116 retries a failed save only at the next `onSettings`. With `requested=true` and a failed write, an offline restart silently drops diagnostics (visible only once LGC6-min ships the state); with `false`, both the write and the delete fallback must fail (DiagRecord.kt:37-42) to leave a `1`, which needs a broken filesystem. Acceptable for LG-MIN; optionally also retry on the next `TraceControl` / `onDiagChanged`. The `off` fallback is correct: `atomicWrite` deletes the old file before its second rename, and `store(false)` deletes on failure, so a `1` survives only if `delete()` itself fails.

6. **Minor (old-phone semantics, question 6).** GlassesRuntime.kt:255: a phone without the field turns the flag OFF and persists `0`. This is what plan 3.4 specifies ("Developer mode off, or an old phone"). Until LGC4P lands, every phone push carries `false` (`HubSettingsStore`/`StateFrameBuilder.settingsFor` never set it), so LGC4 is inert on device. LGC4P must set `diagRecord` from the Developer-mode store at every `pushSettings()` (Hub.kt:371-376), not rely on the stored `HudSettings`, or a phone-app restart would re-send `false` and disable recording.

7. **Minor (log policy deviation).** GlassesLogging.kt:10-18 keeps `capture_diag.log` always-on instead of following `diag_record` as plan 3.1 says ("glasses: the persisted `diag_record`"). This is the right call because of the heartbeat-reader hazard, and it is pinned by `DiagRecordTest.theSourceNeverTouchesPcLogPolicy`, but the plan's 3.1/0A text should record this as a decision so LGC10-min owns the switch.

## Built
1. **Semantics (core).** `WindowRing(seconds, agg, minValidPct = 100)`. A window answers when its full horizon has elapsed since the plan apply / session restart (`n >= seconds`, unchanged warm-up) AND `valid * 100 >= minValidPct * seconds` (Long integers). max, mean and frac are over the VALID seconds only (mean = (sum/valid)/1000; frac = valid ones / valid; max from the monotonic deque, which only ever holds valid slots, so expiry stays correct with gaps). A gap is the sentinel `Int.MIN_VALUE` in the existing Int32 ring (quantised values are clamped to +-2e6), so a valid count (a Kotlin field, not state bytes) is all that was added: **state bytes are unchanged (4*sec, 8*sec for max)**; `stateBytes()` and the 8192 cap accounting did not change.
2. **Wire format.** The lowered op is `{op:win, name, agg, sec[, t], mv}`. `ExprWindows.term` parses `mv`: absent = 100 (strict, so hand-built or pre-3d plans behave as before), present must be an integer 50..100, else the term is malformed and the validator says `expression window term is malformed`. `Term` identity includes `minValidPct`; the limit of 4 terms is counted over that identity (the same window at two tolerances is two terms and two rings, state bytes counted for each). sigSchema stays 2 for window plans (no new schema). The sigSchema-2 window hashes DO change (E2a window plans were never installed): `mv` is written by the compiler when below 100. Schema-1 plans, guard plans without windows and Default capture f5782e0d8610 are untouched (their golden tests are in the green run).
3. **Replay parity.** `CaptureSimulator` runs the same `ExprRunner`, so it inherits the semantics; a sensor stall in a trace leaves gap seconds (`ExprSignals.set` marks the skipped seconds invalid). Test `ReplayWindowParityTest.ReplayWindowToleranceParity`: a 3 s stall in a 20 s window = 18 of 20 valid; answers at 90 (exactly the threshold) and 50, keeps (unavailable) at 91, 100 and with no `mv`; the unstalled trace answers strictly.
4. **Fuzz reference, golden vectors, validator.** `ExprReference` (written independently) now implements the percent rule (horizon elapsed since the first write, valid-only aggregates); `ExprDifferentialFuzzTest` generates windows with `mv` in {absent, 100, 90, 75, 50}. 13 new golden vectors (exactly at the threshold 8/10 at 80, one below at 90, strict 100, all valid at 50, 2 of 10 valid, 9 of 10 elapsed still warming, leading and trailing gaps, max over valid not a zero, frac over valid, 54/60 at 90 answers and 53/60 does not). Validator: range 50..100, identity count <= 4 (`ValidatorChecksTheToleranceRangeAndCountsTermsByIdentity`).
5. **Compile.** `ExprNode.mv` (0 = not written), node key `mv` accepted (`EXPR_BAD_PARAM`: "mv ... must be a whole number between 50 and 100" for a bad value); `ExprProgram.check(defaultMv)`, `ExprLowering.lowerAll(entries, windowMinValidPct)`, `PlanCompiler.compile(..., windowMinValidPct = WindowTolerance.current())`. The compiler writes `mv` ONLY when the effective tolerance (the node's, else the default) is below 100; 100 = strict = absent, so a strict window plan keeps its pre-3d bytes and hash (test `aStrictWindowPlanKeepsItsPreToleranceBytesAndOnlyATolerantOneCarriesMv`; mutation always-write-mv: RED). The golden vectors carry explicit `mv` in hand-written programs and are unaffected.
6. **Try-it.** `POST /api/expr/try`: signal lists may hold `null` (a missing second of that signal); a null in the last position makes a `sig` read UNAVAILABLE while windows still answer by tolerance; a scalar null, a boolean or a string in a list is `400 bad_value`; ragged length still `400 ragged_signals`. The try-it compiles with the global setting unless the graph names `mv`. Side fix: the runner's window freshness test no longer reads feature 0 (gyroMax): `ExprSignals.fresh(now)` (before, a missing gyroMax would have made every window unavailable).
7. **Editor.** The boxed editor's window node has a "Tolerance % (50 to 100) ... empty = the Settings value" field (`mv` key; empty drops the key); the node label shows ` · 80%` when set; the meters count terms by identity including `mv`. The editor does not show the numeric default (no endpoint exposes it): empty means the Settings value, and the compiled plan holds the number.
8. **Global setting.** `window_min_valid_pct` (default 90, 50..100) in `WindowToleranceStore` (SharedPreferences `window_tolerance`, same pattern as `AiCallPaceStore`), ONE `ChoiceRow` "Window tolerance (% of seconds with sensor data)" (50 60 70 80 90 95 100, a stored custom value stays selectable) in Settings > Capture, own card "Capture windows" with a note. Excluded from backup like the pace (`backup_rules.xml`, `data_extraction_rules.xml` x2, `BackupRulesTest` list). `WindowTolerance.provider` (services:ai, an object) is bound in `ContextApp.onCreate` to the store's flow; every compile (canvas compile route, the gated publish `prepare`, replay candidates, try-it) reads `WindowTolerance.current()`. A change affects NEW compiles only; a published plan holds its explicit `mv`.

## Decisions (please review)
1. **Missing `mv` = strict (100) at the glasses/validator, 90 at the compiler.** An old or hand-built plan keeps today's semantics; every compiled plan below 100 states its number (100 is the absent, strict form).
2. **Tolerance in the term identity and the plan hash**, so a settings change makes a new plan hash for any plan that relied on the default. `ReplayCandidates.forHash` therefore also tries 50..100 for pipelines that contain a window, so a published plan's replay candidate survives (a compile that fails at one tolerance, e.g. a duplicate term becoming a fifth, `continue`s to the next: `aReplayCandidateIsFoundEvenWhenAnotherToleranceMakesTheCompileFail`, mutation break: RED; strict plans resolve at 100) a settings change (cost: up to 51 compiles per window pipeline per lookup; a dev-only path). It can resolve a hash at a tolerance nobody published (harmless: still derived from a stored pipeline).
3. **The global setting is a process-wide provider (`WindowTolerance`)** rather than a constructor parameter through `PlanGraph`/`CapturePlanPublisher`/`PlanRoutes`/`ReplayCandidates`/`CanvasExtras` (six call sites). Explicit `windowMinValidPct` parameters exist on `PlanCompiler.compile`, `ExprTry.run`, `ExprLowering.lowerAll` for tests and later threading.
4. **Settings row is a choice row (7 presets + a stored custom value)**, not a free numeric field (typing intermediate values in a live-saved field would fight the user); 50..100 is clamped in the store.
5. **The editor does not display the numeric default.** Empty field = "the Settings value"; the compiled plan carries it (and the plan JSON in the compile result shows `mv`).
6. **A feature value of NaN/inf in one signal is an invalid second for that signal only** (try-it nulls use this); on the device a whole-second stall is still the usual gap.
